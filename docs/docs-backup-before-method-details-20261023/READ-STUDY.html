سؤال 1: إزاي أوصل لاسم خدمة جوه array؟

const services = [
    { id: 1, name: 'Oil Change', price: 450 },
    { id: 2, name: 'Tire Service', price: 300 },

شرح السطور:

  2. {} object لخدمة واحدة. id وname وprice خصائص؛ : يفصل الخاصية عن قيمتها؛ الفواصل تفصل الخصائص.
  3. عنصر آخر في القائمة. النص بين اقتباسات؛ السعر رقم بدون اقتباسات.
  4. ]; نهاية القائمة والتعليمة.
  5. console.log يطبع؛ [0] أول عنصر؛ .name خاصية اسمه. الناتج Oil Change.

بإيدك: اطبع سعر الخدمة الثانية. المتوقع 300.

سؤال إنترفيو: هل const تمنع تغيير خصائص object؟

سؤال 2: أجيب خدمة واحدة باستخدام find إزاي؟

استخدم قائمة السؤال الأول:

const selectedId = 2;
const selected = services.find((service) => {
    return service.id === selectedId;
});
console.log(selected?.price);
  1. selectedId رقم الاختيار.
  2. find تمرّ على العناصر وترجّع أول عنصر ينجح شرطه. (service) => {} callback يستقبل العنصر الحالي.
  3. return يرجّع نتيجة الشرط؛ === مقارنة القيمة والنوع؛ لو true يبقى لقينا العنصر.
  4. قفل الدالة واستدعاء find.
  5. ?. optional chaining: اقرأ price لو selected موجودة؛ لو مفيش نتيجة ترجع undefined بدل خطأ. الناتج هنا 300.

بإيدك: جرّب selectedId = 99 في تعريف المتغير ثم نفّذ المثال من جديد. المتوقع undefined.

غلطة شائعة: المقارنة بين الرقم 2 والنص '2'. حوّل القيمة بـ Number(...) عند الحاجة؛ متلغيش المقارنة الصارمة لمجرد إخفاء المشكلة.

سؤال إنترفيو: find ترجع إيه لو مفيش تطابق؟

الإجابةترجع `undefined`، مش array فاضية.

المصدر الفعلي للفكرة: بحث السيارة، بحث سعر الفرع.

سؤال 3: أجيب الطلبات المؤكدة فقط باستخدام filter؟

const appointments = [
    { id: 1, status: 'confirmed' },
    { id: 2, status: 'requested' },

const confirmed = appointments.filter((item) => item.status === 'confirmed');
console.log(confirmed.length);

1–4. قائمة فيها object لكل موعد، وكل واحد له id وstatus. 5. filter تنشئ array جديدة بكل العناصر اللي شرطها true. هنا arrow function مختصرة: التعبير بعد => بيترد تلقائيًا بدون return. 6. .length عدد عناصر النتيجة؛ الناتج 1.

بإيدك: اعرض الطلبات requested. المتوقع array فيها الموعد الثاني.

غلطة شائعة: توقّع object واحد من filter. حتى لو فيه نتيجة واحدة، الناتج array.

سؤال إنترفيو: الفرق بين find وfilter؟

الإجابة`find` أول عنصر أو undefined؛ `filter` قائمة بكل المطابقات أو قائمة فاضية.

سؤال 4: إزاي أحوّل قائمة الخدمات لقائمة أسماء بـ map؟

باستخدام services من السؤال الأول:

  1. map تبني array جديدة؛ لكل خدمة الدالة بترجّع name فقط. عدد عناصر الناتج يساوي عدد عناصر الأصل هنا.
  2. يطبع ['Oil Change', 'Tire Service'].

بإيدك: رجّع الأسعار بدل الأسماء. المتوقع [450, 300].

غلطة شائعة: تكتب callback بـ {} وتنسى return، فتلاقي النتيجة قيم undefined.

سؤال إنترفيو: ليه مش forEach؟

الإجابة`map` ترجع قائمة النتائج. `forEach` تنفّذ callback لكل عنصر لكن ترجع undefined، ومش بتجهّز قائمة نتائج تلقائيًا.

سؤال 5: أحسب إجمالي سلة بـ reduce إزاي؟

const cart = [
    { price: 50, quantity: 2 },
    { price: 30, quantity: 1 },
];
const total = cart.reduce((sum, item) => {
    return sum + item.price * item.quantity;
}, 0);
console.log(total);

1–4. بيانات سلة تدريبية؛ كل سطر سعر وكمية. 5. reduce تجمع القائمة في نتيجة؛ sum الإجمالي المتراكم وitem السطر الحالي. 6. * حساب قيمة السطر؛ + إضافتها للإجمالي؛ return يمرّر الإجمالي للفة التالية. 7. 0 القيمة الابتدائية لـ sum؛ مهمة كمان علشان السلة الفاضية ترجع صفر. 8. الناتج 130: أول سطر 100 وبعده 30.

بإيدك: زوّد الكمية الأولى لـ 3. المتوقع 180.

غلطة شائعة: تخزّن السعر '$50' ثم تعمل ضرب. خزّن رقمًا، واعرض العملة عند العرض. إجمالي المتصفح للعرض؛ السيرفر لازم يعيد حساب سعر الطلب الحقيقي.

سؤال إنترفيو: ينفع أثق في total اللي المتصفح بعته؟

  1. بيانات السيارة الأصلية.

سؤال 7: أتعامل مع Promise وasync/await إزاي؟

نفّذ ده من Console صفحة Pizza المحلية، مش من Cloudflare Demo. الطلب GET قراءة فقط:

async function loadMenu() {
    try {
        const response = await fetch('/api/menu');
        if (!response.ok) throw new Error('Menu request failed');
        const data = await response.json();
        console.log(data.items.length);
    } catch (error) {
        console.log(error.message);
    }
}
loadMenu();
  1. async تجعل الدالة ترجع Promise وتسمح باستخدام await داخلها.
  2. try بداية الكود اللي ممكن يفشل.
  3. fetch ترجع Promise؛ await تنتظر النتيجة داخل الدالة، من غير تجميد واجهة المتصفح.
  4. ! نفي؛ لو حالة HTTP مش ناجحة نرمي Error. fetch لا ترمي خطأ تلقائيًا لمجرد 404 أو 500.
  5. response.json() عملية أخرى asynchronous لقراءة JSON وتحويله لقيمة JavaScript.
  6. اطبع عدد المنتجات؛ يعتمد على الكتالوج الحالي. 7–8. catch تستقبل الخطأ وتطبع رسالته. 9–10. إغلاق البلوكات والدالة.

غلطة شائعة: تنسى await response.json() فتتعامل مع Promise كأنها بيانات المنتجات.

الإجابةلأ؛ بتعلّق استمرار الدالة async لحد النتيجة، وباقي المهام تقدر تشتغل.

13 — Vue: نفس أمثلة AutoCare خطوة خطوة

الفهرس · قبل الدرس: JavaScript.

المصدر الأساسي AutoCare App.vue. الأمثلة الصغيرة تدريب مبسّط على نفس الفكرة، مش نقل حرفي لكل التطبيق. نفّذ كل سؤال في مكوّن تدريب داخل مشروعك اليدوي؛ متستبدلش App.vue الأصلي الكبير.

سؤال 1: أغيّر النص لما أضغط زر إزاي؟

ده مكوّن تدريب كامل صغير:

<script setup>
import { ref } from 'vue';
const menuOpen = ref(false);
</script>

<template>
    <button type="button" @click="menuOpen = !menuOpen">
        {{ menuOpen ? 'Close' : 'Menu' }}
    </button>
</template>

شرح السطور:

  1. <script setup> جزء JavaScript؛ تعريفاته متاحة في template.
  2. import استيراد أداة ref من Vue.
  3. حالة reactive تبدأ false. const يمنع إعادة إسناد المرجع، مش تغيير .value.
  4. نهاية script.
  5. بداية واجهة المكوّن.
  6. زر عادي؛ @click ينفّذ التعبير عند الضغط؛ ! تعكس true/false. في template Vue تفك ref تلقائيًا.
  7. {{ }} عرض نص؛ ? : اختيار بين نصين حسب الحالة. 9–10. قفل الزر وtemplate.

بإيدك: اضغط مرتين. المتوقع Close ثم Menu.

غلطة شائعة: في JavaScript نكتب menuOpen.value؛ في template هنا menuOpen بدون value.

سؤال إنترفيو: الفرق بين متغير عادي وref؟

الإجابةref تعطي Vue حالة قابلة للتتبع لتحديث الواجهة عند تغيّرها؛ تغيير متغير عادي مش وسيلة reactive لتحديث العرض.

سؤال 2: أعرض قائمة خدمات وأخزّن الاختيار؟

داخل script للمكوّن التدريبي، احتفظ باستيراد ref مرة واحدة وأضف:

const services = [
    { id: 1, name: 'Oil Change', price: 450 },
    { id: 2, name: 'Tire Service', price: 300 },
];
const selectedServiceId = ref('');

1–4. قائمة object لكل خدمة، وفيها معرّف واسم وسعر. 5. الاختيار يبدأ فارغًا؛ ده المتغير اللي v-model هتحدّثه.

داخل template:

<select v-model="selectedServiceId" aria-label="Service">
    <option disabled value="">Choose a service</option>
    <option v-for="service in services" :key="service.id" :value="service.id">
        {{ service.name }}
    </option>
</select>
  1. v-model تربط قيمة القائمة بالحالة في الاتجاهين؛ aria-label اسم مفهوم للقائمة.
  2. اختيار إرشادي قيمته فارغة؛ disabled يمنع اختياره.
  3. v-for تكرر option؛ service العنصر الحالي؛ :key هوية مستقرة وفريدة؛ :value يربط رقم id الحقيقي، مش نص service.id.
  4. اسم الخدمة المعروض للمستخدم. 5–6. إغلاق العناصر.

بإيدك: أضف <p>{{ selectedServiceId }}</p> بعد القائمة. المتوقع 1 أو 2 عند الاختيار.

غلطة شائعة: value="service.id" بدون النقطتين يخزّن النص نفسه لكل الخيارات.

سؤال إنترفيو: هل key هي القيمة اللي select تختارها؟

الإجابةلأ؛ key لتتبّع Vue للعناصر، value هي قيمة الاختيار.

سؤال 3: أظهر السعر تلقائيًا باستخدام computed؟

عدّل الاستيراد إلى import { ref, computed } from 'vue'; وأضف بعد القائمة والحالة:

const selectedService = computed(() => {
    return services.find((service) => {
        return service.id === selectedServiceId.value;
    });
});
  1. متغير computed قيمته ناتج الدالة؛ بيتابع selectedServiceId اللي اتقرأت أثناء الحساب.
  2. find ترجع أول object يحقق الشرط.
  3. === مقارنة صارمة بين id الخدمة وقيمة الاختيار؛ .value لقراءة ref داخل JavaScript. 4–5. إغلاق callback واستدعاء find، ثم computed.

وفي template بعد select:

<div v-if="selectedService">
    <p>{{ selectedService.name }}</p>

1. يعني إيه array وobject؟

مثال تدريبي من فكرة خدمات AutoCare؛ مصدر الفكرة:

const services = [
    { id: 1, name: 'Oil Change', price: 450 },
    { id: 2, name: 'Tire Service', price: 300 },
];
console.log(services[0].name);
  • const: اسم مش هنعيد إسناده؛ مش معناه إن محتوى object مستحيل يتغير.
  • services: اسم القائمة؛ = إسناد، و[] حدود array.
  • {} object واحد؛ id/name/price خصائص، و: يفصل الاسم عن القيمة.
  • [0] أول عنصر، و.name خاصية الاسم؛ الناتج Oil Change.
  • ; نهاية تعليمة؛ الفواصل تفصل الخصائص والعناصر.

إنترفيو: array قائمة مرتبة؛ object يجمع خصائص كيان واحد.

2. إيه الفرق بين = و=== و! و&&؟

مثال تدريبي جديد مرتبط بـ اختيار الفرع:

const branchId = 2;
const isSelected = branchId === 2;
const canOrder = isSelected && true;
console.log(!canOrder);
  • = إسناد؛ === مقارنة القيمة والنوع.
  • isSelected تساوي true.
  • && في المثال يرجّع نتيجة الطرف التاني لو الأول truthy؛ مش عامل تحويل تلقائي لكل نتيجة إلى Boolean.
  • ! يقلب القيمة المنطقية؛ الطباعة false.

تمرين: غيّر branchId إلى النص '2'. المتوقع: المقارنة false والطباعة true.

خطأ شائع: if (branchId = 2) إسناد مش مقارنة.

إنترفيو: strict equality ما بتحوّلش النوع قبل المقارنة؛ افهم مصدر القيمة قبل استخدام Number().

3. إيه الفرق بين find وfilter وmap وforEach؟

استعمل services من سؤال 1. مثال تدريبي مبسّط؛ كود السلة الحقيقي:

const chosen = services.find((service) => service.id === 2);
const affordable = services.filter((service) => service.price < 400);
const names = services.map((service) => service.name);
services.forEach((service) => console.log(service.name));
  • find: أول object مطابق، أو undefined لو مفيش.
  • filter: array جديدة بالعناصر المطابقة؛ هنا خدمة الإطارات بس.
  • map: array جديدة من نتائج التحويل؛ هنا اسمان.
  • forEach: ينفذ callback لكل عنصر؛ مش بيرجّع array النتائج.
  • (service) => ...: callback؛ service العنصر الحالي، والاسم اختيارنا.

تمرين: هات الخدمات الأعلى من 1000. المتوقع: filter ترجع []، مش undefined.

خطأ شائع: استخدام map للطباعة بس، أو توقع إن find ترجع قائمة.

إنترفيو: اختار الدالة بناءً على شكل النتيجة المطلوبة، مش الاسم اللي حافظه.

4. يعني إيه spread وdestructuring؟

مثال مبسّط من تحديث السلة:

const item = { id: 1, quantity: 1, price: 100 };
const updated = { ...item, quantity: 2 };
const { price, quantity } = updated;
console.log(price * quantity);
  • ...item ينسخ الخصائص إلى object جديد؛ النسخة shallow مش deep.
  • quantity: 2 مكتوبة بعد spread، فبتستبدل القيمة القديمة.
  • { price, quantity } = updated تفكيك: اعمل متغيرين من خاصيتين.
  • الطباعة 200؛ item.quantity لسه 1.

تمرين: اعكس ترتيب { quantity: 2, ...item }. المتوقع: quantity ترجع 1 لأن آخر خاصية تكسب.

خطأ شائع: تعديل item.quantity++ مباشرة ثم توقع React يكتشف نفس المرجع تلقائيًا.

إنترفيو: immutable update معناه ننتج قيمة جديدة بدل تعديل القديمة؛ spread لا يفصل nested objects تلقائيًا.

5. يعني إيه optional chaining وnullish coalescing؟

مثال تدريبي من فكرة branchOption:

const branch = null;
const name = branch?.name ?? 'Choose a branch';
const fee = 0;
console.log(fee ?? 20);
console.log(fee || 20);
  • ?. توقف الوصول لو القيمة null أو undefined بدل error.
  • ?? يستخدم البديل فقط مع null/undefined؛ اسم الفرع هنا النص البديل.
  • fee ?? 20 يطبع 0؛ الصفر قيمة مقصودة.
  • fee || 20 يطبع 20 لأن || يستخدم البديل مع أي falsy مثل صفر والنص الفاضي.

تمرين: غيّر fee إلى undefined. المتوقع: الاتنين 20.

خطأ شائع: اعتبار || و?? متطابقين في الأسعار والكميات.

إنترفيو: ?. يمنع خطأ الوصول في مسار قد يكون مفقودًا؛ مش validation للبيانات.

6. يعني إيه Promise وasync/await؟

مثال تدريبي مبسّط؛ المصدر الفعلي للطلبات:

async function loadMenu() {
    const response = await fetch('/api/menu');
    if (!response.ok) throw new Error('Menu request failed');
    const data = await response.json();
    return data;
}
  • async تخلي الدالة ترجع Promise؛ Promise تمثل نتيجة قد تكتمل أو تفشل لاحقًا.
  • fetch يبدأ طلب HTTP ويرجع Promise.
  • await ينتظر داخل الدالة دي؛ مش بيجمّد واجهة المتصفح كلها.
  • response.ok نجاح HTTP؛ fetch مش بيرفض Promise تلقائيًا لمجرد 404 أو 422.
  • throw new Error ينقل التنفيذ لمسار الخطأ؛ استخدم try/catch عند الاستدعاء.
  • response.json() قراءة body كـ JSON؛ غير JSON.stringify اللي يحوّل object إلى نص.

تمرين: توقع نتيجة URL غير موجود. المتوقع: الاستثناء اللي كتبناه، مش بيانات منيو.

خطأ شائع: استخدام data.items قبل انتظار Promise.

إنترفيو: await يبسّط كتابة async code؛ ما بيحوّلش طلب الشبكة لعملية synchronous على الـ main thread.

7. إيه state وprops وcomputed وeffect؟

  • State: بيانات ممكن تتغير وتؤثر على العرض؛ Vue ref، React useState.
  • Props: مدخلات الأب للابن؛ الطفل ما يغيّرش props مباشرة.
  • Computed / derived value: نتيجة مشتقة، مثل الخدمة المطابقة للـ id؛ مش بنكرر تخزين نفس الحقيقة بدون داعي.
  • Effect: مزامنة مع حاجة خارج حساب الواجهة: listener أو timer أو network.
  • Component: جزء واجهة له inputs وعرض وسلوك؛ مش لازم يبقى ملف ضخم.

سؤال: Vue ref وReact useRef نفس الحاجة؟

الإجابة

لأ. تحديث Vue ref المستخدم في العرض ممكن يحدّث الواجهة. تغيير React ref.current لا يعمل render بحد ذاته. React state هو المقارنة الأقرب هنا.

8. HTTP وbackend: كل كلمة معناها إيه؟

  • Request: رسالة طالعة للسيرفر؛ Response: رده.
  • Route: ربط method وURL بكود؛ Controller: يستقبل ويُنسّق الرد.
  • GET: قراءة؛ POST: إرسال/إنشاء؛ PATCH: تعديل جزئي؛ semantics مش بديل للحماية.
  • API endpoint: مثل POST /api/orders؛ وجود /api في الاسم لا يفرض auth تلقائيًا.
  • Validation: هل شكل وقيم البيانات مقبولة؟ Authorization: هل الشخص مسموح له بالفعل ده؟
  • Authentication: إثبات الهوية؛ Session: ربط حالة الدخول بكوكي المتصفح في النسخة المحلية.
  • CSRF: منع طلب تغيير مزور من موقع تاني مستغل جلسة المستخدم؛ مش حماية من كل الهجمات.
  • 401: لم يتم تسجيل الدخول؛ 403: غير مسموح؛ 404: غير موجود؛ 409: تعارض؛ 422: validation فشلت؛ 500: خطأ سيرفر.

المصدر: routes، auth، request helper.

9. Database وpayment: الأسئلة اللي تفرّق في الإنترفيو

  • Model/Eloquent: تمثيل البيانات والعلاقات بكود PHP؛ Order.
  • Migration: تعريف تغيير في بنية DB، مش البيانات نفسها.
  • Seeder: إدخال بيانات بداية/demo؛ مش مصدر الأسرار.
  • Foreign key: مرجع لصف في جدول تاني؛ مثل order → branch.
  • Pivot: ربط many-to-many؛ branch_menu_item يحمل السعر والتوفر للفرع.
  • Transaction: عمليات DB تنجح سوا أو تتراجع سوا؛ مش ضمان لنجاح خدمة Stripe الخارجية.
  • Webhook: طلب من خدمة خارجية لسيرفرك؛ لازم تتحقق من توقيعه.
  • Idempotency: تكرار نفس العملية المقصودة لا ينتج أثرًا مكررًا؛ مش ادعاء إن كل race condition اتحلت.

المصدر: OrderCreator، PaymentController.

2. AutoCare: app.js بيختار App.vue إزاي؟

مصادر: routes، Blade، app.js.

const isGarage = location.pathname.replace(/\/$/, '') === '/my-garage';
document.title = isGarage ? 'My Garage | AutoCare Pro' : 'AutoCare Pro | Car care, with clarity';

    ? import('./components/GarageDashboard.vue')
    : import('./components/App.vue'));

createApp(Page).mount('#app');

السياق: الملف مستورد فيه createApp وdefineAsyncComponent من Vue فوق المقتطف.

  • === يرجع Boolean؛ /my-garage/ يتطبع لـ /my-garage قبل المقارنة.
  • condition ? A : B ternary يختار واحد من قيمتين؛ هنا عنوان الصفحة ثم المكوّن.
  • defineAsyncComponent يأخذ loader؛ import(...) الديناميكية ترجع Promise وتتيح تحميل chunk حسب الاختيار.
  • mount('#app') يطابق <div id="app"> في Blade.

مفيش Vue Router في الأسلوب ده. اختيار root component بيحصل وقت بدء التطبيق، والتنقل العادي بين الصفحتين يعمل document navigation.

تمرين: افتح / ثم /my-garage/ وراقب document title. المتوقع: عنوانان ومكوّنان مختلفان رغم نفس Blade view محليًا.

سؤال إنترفيو: إمتى أستخدم dynamic import؟ الإجابة: لما فصل التحميل مفيد، مع handling لحالات الانتظار والفشل؛ مش كل import لازم يبقى lazy.

1. سؤال: الواجهة بتبدأ منين بالضبط؟

مقتطف فعلي من app.blade.php:

@vite(['resources/css/app.css', 'resources/js/app.jsx'])

السطر يولد روابط تحميل CSS وJavaScript. @vite تعليمة Laravel على السيرفر، مش JavaScript بيشغله المتصفح. داخل القائمة مساران: stylesheet ومدخل React. وقت التطوير Vite يقدم الملفات، وبعد build Laravel يستخدم manifest للوصول للأسماء المبنية. ملف Blade يحتوي على <div id="root"></div>، وهي المساحة اللي React هيعرض فيها التطبيق.

ReactDOM.createRoot(document.getElementById('root')).render(

);

  3. <App /> يشغّل المكوّن الرئيسي؛ الحرف الكبير يميّزه عن عنصر HTML عادي.
  4. قفل غلاف StrictMode.
  5. نهاية استدعاء render. JSX في الوسط بيتحوّل بواسطة build tool لاستدعاءات JavaScript.

تطبيق يدوي: افتح Blade وحدد root ثم ابحث عن نفس النص في app.jsx. في نسخة تدريبية لو غيرت الاسم في طرف واحد فقط، المتوقع إن التطبيق يفشل في التركيب بدل ما ينشئ العنصر تلقائيًا. رجّع الاسم فورًا.

3. سؤال: إزاي الأب يتحكم في ظهور الـ Navbar بـ props؟

مقتطف فعلي من AppShell:

<Navbar
    isVisible={!isHome || heroReady}

    animateReveal={isHome}
/>

  5. قفل الاستدعاء.

export default function Navbar({ isVisible = true, reduceMotion = false, animateReveal = false }) {

ده سطر افتتاح function، مش المكوّن كله: export default يسمح باستيراده كالتصدير الأساسي، وNavbar اسم المكوّن. { ... } داخل الأقواس اسمها destructuring: تفك object الـ props لمتغيرات. = true و= false قيم افتراضية تستخدم لو prop غير مرسلة أو undefined؛ لو الأب مرر false صراحة، القيمة الافتراضية مش هتغيّرها.

غلطة شائعة: isVisible="false" تبعت نصًا غير فاضي، والنص ده truthy مش Boolean false. استخدم الأقواس للقيمة المنطقية.

السطر الأول يستمع لتغييرات التخزين من مستند آخر مناسب، مش لنفس الصفحة اللي كتبت. الثاني يستمع لحدث المشروع اليدوي داخل نفس التبويب؛ الاسم wtc-cart-updated. السطر الفاضي فصل. الرابع يرجع cleanup للـ effect. الخامس والسادس يزيلوا نفس الحدث ونفس مرجع الدالة. السابع يقفل cleanup. syncCartCount في الأصل تنادي setCartCount(getCartCount())، والدالة تحسب مجموع الكميات بـ reduce، مش عدد السطور.

مثال مبسّط من Navbar في AutoCare App.vue، اكتبه في مكوّن Vue تدريبي منفصل فقط، مش داخل React:

const navbarScrolled = ref(false);
function updateNavbar() {
    navbarScrolled.value = window.scrollY > 24;
}
onMounted(() => {
    updateNavbar();
    window.addEventListener('scroll', updateNavbar, { passive: true });
});
onBeforeUnmount(() => window.removeEventListener('scroll', updateNavbar));

يلزم استيراد ref, onMounted, onBeforeUnmount من vue داخل script setup. الأول حالة، الثاني تعريف دالة، الثالث يقارن مسافة النزول ويحدث الحالة، الرابع يقفل الدالة. الخامس يبدأ lifecycle hook؛ السادس يضبط الحالة فورًا؛ السابع يستمع للتمرير وpassive تعلن إن المعالج مش هيمنع الحدث. الثامن يقفل hook؛ التاسع ينظف قبل الإزالة.

تطبيق: تتبّع add/remove بنفس اسم الدالة في المشروعين. المتوقع: لا تراكم listeners بعد خروج/رجوع. غلطة شائعة: استخدام arrow function جديدة في remove؛ مش نفس المرجع، فلا تلغي القديمة.

سؤال إنترفيو: التشابه الأساسي بين React وVue هنا؟

2. سؤال: إزاي أجيب سعر المنتج في الفرع المختار؟

مقتطف فعلي من CatalogContext.jsx:

export function branchOption(item, branchId) {
    return item?.branch_options?.find((option) => Number(option.branch_id) === Number(branchId)) || null;
}

السطر الأول يعرّف دالة قابلة للاستيراد بـ export، اسمها branchOption، ومدخلاتها المنتج ومعرّف الفرع. السطر الثاني بيرجّع أول خيار مطابق أو null. السطر الثالث يقفل الدالة.

نفك السطر الطويل: item?.branch_options يقرأ خيارات الفروع لو المنتج موجود. ?.find مايناديش البحث لو القائمة نفسها null أو undefined. find يمر على الخيارات ويرجّع object واحد؛ option اسم العنصر الحالي. => تعريف callback قصيرة. Number(...) يحوّل المعرّفات لأرقام، علشان '2' و2 يتقارنوا بنفس النوع. === مقارنة صارمة. || null بديل لما مفيش تطابق. ده يتحمل غياب البيانات، لكنه مش تحقق كامل من صحة شكل الرد.

تطبيق يدوي: غيّر البحث إلى === 3، واطبع option بدل option.price. المتوقع: undefined، لأن find ما لقتش عنصر. الدالة الأصلية تحول النتيجة إلى null، فلازم المتصل يفحصها قبل قراءة السعر.

غلطة شائعة: استخدام filter ثم كتابة .price؛ filter بيرجّع array مش object.

سؤال إنترفيو: الفرق بين find وfilter؟

find يرجّع أول عنصر مطابق أو undefined. filter يرجّع array بكل المطابقات، وممكن تكون فاضية. اختار حسب شكل النتيجة اللي محتاجه، مش حسب الاسم الأسهل.

كل سطر: الأول يبدأ العنصر. الثاني key هوية React؛ تغييره يعيد إنشاء العنصر، مش timer. الثالث يربط العنصر بـ videoRef.current. الرابع كلاسات التنسيق، مش state. الخامس عنوان الملف؛ /videos داخل public، وجزء ?v= نسخة URL لكسر cache القديم. السادس يكتم الصوت ويساعد autoplay لكنه مش ضمان تشغيل. السابع يطلب تشغيلًا داخل الصفحة على الموبايل. الثامن تلميح للمتصفح لتحميل البيانات، مش أمر مضمون. التاسع ينادي الدالة عند انتهاء الفيديو. العاشر يناديها عند خطأ حتى ما يفضلش الموقع فاضي. الحادي عشر يخفي الفيديو الزخرفي عن قارئ الشاشة، مش عن النظر. الأخير يقفل العنصر.

تطبيق يدوي: اقرأ const video = videoRef.current في الـ effect الأصلي. في نسخة تدريبية فقط أضف زرًا ينادي videoRef.current?.pause()؛ ?. يحمي من عدم وجود العنصر. المتوقع: الوقوف من غير ما تتحول قيمة ref إلى state.

غلطة شائعة: كتابة videoRef.play()؛ العنصر الحقيقي في .current مش كائن الـ ref نفسه.

سؤال إنترفيو: إمتى تستخدم DOM ref؟

لعمل imperative محتاج العنصر نفسه، زي focus أو قياس الأبعاد أو play/pause. لتغيير النص أو إظهار قائمة استخدم state وJSX بدل تعديل DOM يدويًا جنب React.

2. سؤال: الطفل بيبلغ الأب إن الفيديو جاهز إزاي؟

مقتطف فعلي من app.jsx داخل AppShell:

const [heroReady, setHeroReady] = useState(false);

const revealHero = useCallback(() => {
    setHeroReady(true);
}, []);

السطر الأول يفك نتيجة useState إلى قيمة وsetter، والبداية false. السطر الفاضي للفصل فقط. الثالث يعرّف callback ثابتة المرجع عبر renders طالما الاعتماديات لم تتغير. الرابع يطلب تحديث الحالة إلى true. الخامس يقفل الدالة ويحدد اعتماديات فاضية؛ setter الخاص بـ React ثابت فلا نحتاج إضافته. useCallback لا ينفّذ الدالة؛ بيرجع نسخة ذات مرجع محفوظ.

الأب يمرر revealHero إلى Home باسم onHeroReady. مقتطف فعلي من Home يمرره للـ Hero:

<HeroSection
    isReady={heroReady}
    onReady={onHeroReady}
    reduceMotion={reduceMotion}
/>

الأول اسم المكوّن، الثاني الحالة نازلة من الأب، الثالث الدالة نازلة تحت اسم onReady، الرابع تفضيل تقليل الحركة، الخامس قفل المكوّن. الأسماء بعد = تعبيرات JavaScript داخل {}، مش نصوص.

مقتطف فعلي داخل Hero:

const revealContent = React.useCallback(() => {
    if (hasRevealedRef.current) return;
    hasRevealedRef.current = true;
    onReady();
}, [onReady]);

الأول تعريف callback؛ الثاني يمنع النداء المكرر لو كنا كشفنا المحتوى؛ الثالث يسجل الكشف؛ الرابع ينادي الدالة اللي الأب بعتها؛ الخامس يعيد المرجع لو onReady اتغيرت. الطفل مش بيعدل prop اسمها isReady؛ بيطلب من الأب يحدّث الحالة.

تطبيق: ارسم على ورقة AppShell → Home → HeroSection للـ props، وسهم رجوع لنداء callback. المتوقع: تقدر تقول مين صاحب الحالة ومين بيطلب تغييرها. غلطة شائعة: onReady={onHeroReady()} يشغّل الدالة أثناء render بدل تمريرها.

سؤال إنترفيو: ليه الحالة في الأب؟

لأن Navbar وHero محتاجين نفس المعلومة. رفع الحالة لأقرب أب مشترك يمنع نسختين مختلفتين من «جاهز». في React التواصل لفوق غالبًا callback prop؛ مش تعديل props مباشرة.

3. سؤال: إيه علاقة play بـ Promise وتنظيف الـ effect؟

مقتطف فعلي من effect الفيديو؛ المتغيرات والدوال معرفة قبله في نفس effect:

const playPromise = video.play();
playPromise?.catch(() => {
    if (isCurrentPlayback) {
        revealContent();
        window.cancelAnimationFrame(animationFrameId);
    }
});
  1. ننادي تشغيل الفيديو ونحفظ Promise التشغيل؛ دي مش Promise انتهاء الفيديو.
  2. ?.catch يتعامل مع رفض التشغيل لو فيه Promise؛ الـ arrow function تتنفذ عند الرفض، مثل رفض autoplay.
  3. نفحص إن دورة التشغيل الحالية ما اتلغتش.
  4. نكشف النص علشان الموقع يفضل قابلًا للاستخدام لو الفيديو فشل.
  5. نوقف frame callback المحفوظة؛ ملهاش داعي بعد الرفض. 6–7. قفل الشرط ثم callback واستدعاء catch.

مقتطف فعلي من نهاية نفس effect:

return () => {
    isCurrentPlayback = false;
    window.cancelAnimationFrame(animationFrameId);
};

الأول يرجع cleanup لReact، مش نتيجة شاشة. الثاني يغيّر علمًا محليًا علشان رد Promise المتأخر ما يشغّلش كشف قديم. الثالث يلغي callback الرسم المجدولة. الرابع نهاية الدالة. isCurrentPlayback متغير داخل effect، مش state؛ قيمته وظيفتها حماية دورة تشغيل محددة.

تطبيق يدوي: في نسخة تجريبية غيّر عنوان الفيديو مؤقتًا لملف غير موجود ثم ارجع العنوان الصحيح. المتوقع: النص يظهر عن طريق onError بدل صفحة بلا محتوى. جرّب الانتقال لصفحة Menu أثناء التشغيل؛ الـ effect يتنضف. ما تضيفش cleanup ثانية منفصلة من غير ما تفهم متغيراتها.

غلطة شائعة: الاعتماد على autoplay وعدم توفير fallback. وبرضه flag الإلغاء لا توقف الشبكة ولا تقوم تلقائيًا بعمل video.pause()؛ cleanup الحالية تلغي callback وتمنع ردها المتأخر فقط.

سؤال إنترفيو: requestAnimationFrame هو setInterval؟

لأ، requestAnimationFrame يطلب callback قرب رسم الإطار القادم، ولمواصلة الدورة لازم تعيد طلبه. setInterval يعمل بتوقيت زمني. الاتنين محتاجين cleanup مناسبة، ومش مضمون يتنفذوا بانتظام كامل في تبويب بالخلفية.

4. سؤال: إزاي النص يظهر تدريجيًا من غير تعديل DOM يدوي؟

مثال مبسّط من تعريف heroRevealItem في Home؛ اختصرنا كتابة transition إلى سطر واحد بنفس القيم:

const heroRevealItem = {
    hidden: {
        opacity: 0,
        y: 25,
    },
    visible: {
        opacity: 1,
        y: 0,
        transition: { duration: 0.6, ease: 'easeOut' },
    },
};

الأول object إعدادات، مش دالة. الثاني حالة اسمها hidden. الثالث شفافية صفر. الرابع إزاحة رأسية 25px. الخامس يقفل الحالة. السادس يبدأ visible. السابع شفافية كاملة. الثامن يرجع لموضع الصفر. التاسع object لتوقيت الحركة: duration بالثواني وeaseOut يبطئ قرب النهاية. العاشر يقفل visible، والحادي عشر يقفل object.

مثال مبسّط من JSX للـ Hero: داخل المكوّن، بعد التأكد إن isReady وreduceMotion props موجودة، وmotion مستوردة من framer-motion:

{isReady && (

        Hot Stone Pizza

الأول conditional rendering: لو جاهز، أضف العنصر. الثاني motion.h1 عنوان تديره مكتبة الحركة؛ variants يمرر الإعدادات، وternary يختار تعطيل البداية الحركية عند طلب تقليل الحركة، وanimate يحدد الحالة النهائية. الثالث النص. الرابع يقفل العنوان. الخامس يقفل التعبير. الأصل يستخدم container مع stagger لظهور العناصر بالتتابع؛ المثال اختصره لعنوان واحد.

تطبيق: غيّر y: 25 إلى 0 في نسخة تدريبية فقط. المتوقع: تلاشي بدون انتقال رأسي. غلطة شائعة: استخدام اسم show في animate بينما التعريف اسمه visible.

سؤال إنترفيو: ليه نهتم بتقليل الحركة؟

تفضيل accessibility لازم نحترمه، مش كل مستخدم يستحمل نفس الأنيميشن. الأصل يمرر useReducedMotion للانتقالات؛ الفيديو نفسه لا يتوقف تلقائيًا بهذا prop في التنفيذ الحالي، ودي نقطة لازم ما نخلطش بينها وبين تعطيل الحركة بالكامل.

بعد ما تشرح الأمثلة: ارجع لـ Navbar والأب المشترك. لا تحتاج دراسة CSS الطويل أو معادلة تبطيء الفيديو قبل فهم refs وcallbacks والتنظيف.

06 — أسئلة وأمثلة: الـ request بيمشي في Laravel إزاي؟

الترتيب اللي هتحتاج تفهمه في مقابلة: URL وHTTP method يختاروا route؛ middleware تفحص الوصول؛ Form Request تتحقق من البيانات؛ controller ينسّق التنفيذ؛ service تنفّذ منطقًا قابلًا لإعادة الاستخدام؛ وفي الآخر response.

خد سؤال واحد في المرة. الأمثلة المختصرة مش ملفات بديلة. هنا بندرس Laravel الحقيقي في Pizza CRM، مش ملفات الـ frontend demo اللي بتحاكي API.

1. مين بيوصل /api/staff/orders/7 بالدالة المناسبة؟

مقتطف فعلي من routes/web.php، موجود داخل مجموعة prefix('api') بالفعل.

Route::middleware(['auth', 'role:staff,admin'])->prefix('staff')->group(function () {
    Route::get('/orders', [StaffOrderController::class, 'index']);
    Route::get('/orders/{order}', [StaffOrderController::class, 'show']);
    Route::patch('/orders/{order}/status', [StaffOrderController::class, 'updateStatus']);
});

كل سطر بيعمل إيه؟

  • Route::middleware([...]): أضف فحوصات قبل تنفيذ دوال المجموعة. auth للجلسة، وrole:staff,admin لقبول دور موظف أو مدير حسب middleware المشروع.
  • ->prefix('staff'): ضيف /staff قبل مسارات المجموعة. ومع الـ prefix الخارجي النتيجة تبدأ بـ /api/staff.
  • ->group(function () {: اجمع المسارات داخل دالة؛ { يبدأ جسم المجموعة.
  • Route::get('/orders', [...]): طلب قراءة القائمة ينادي index. الـ array فيها اسم class ثم اسم method كنص.
  • StaffOrderController::class: هات اسم class الكامل؛ use في أول الملف يعرّف الاسم المختصر.
  • '/orders/{order}': الجزء بين {} قيمة متغيرة. مع parameter اسمه $order ونوعه Order في method، Laravel يحمّل السجل: route model binding.
  • Route::patch(...): تعديل جزئي للحالة، مش طلب قراءة. يوجّه إلى updateStatus.
  • });: قفل الدالة والمجموعة.

لو سجل 7 مش موجود، binding يرجع404. لو موجود لكن تابع لفرع تاني، فيه فحص صلاحيات مستقل في controller؛ وجود السجل لا يعني السماح بعرضه.

ملفات web.php محمّلة من bootstrap/app.php. المسار يبدأ بـ /api لكن ما زال داخل web middleware، ولذلك المشروع يستخدم sessions وCSRF؛ الاسم وحده مش بيحوّله إلى token API. الطلب يدخل Laravel أصلًا من public/index.php، مش من ملف الـ controller مباشرة.

نفّذ بإيدك: حدد المسار والـ method والدالة لطلب قائمة الموظفين ولتغيير حالة الطلب 7. استخدم قراءة الكود أو Network؛ ما تبعتش PATCH عشوائي لطلب فعلي.

المتوقع: GET /api/staff/orders ينادي index؛ PATCH /api/staff/orders/7/status ينادي updateStatus بعد فحوص الوصول.

غلطة شائعة: تجرب POST على route مكتوبة PATCH، أو تعتبر model binding بديل authorization. method غلط قد يرجّع405 بدل404.

سؤال إنترفيو: هل route لازم تستخدم controller؟

لأ، ممكن closure أو Route::view. Controller مناسب لتنظيم معالجة الطلبات، خصوصًا لما فيها منطق أو اعتماديات أو أكثر من إجراء مترابط.

2. ليه الـ controller مش بيحسب الأسعار بنفسه؟

مثال مبسّط من OrderController.php. المثال يحتفظ بفصل الدفع الكاش عن الكارت؛ الأصل يستخدم ValidationException بدل الرد المختصر، ويطلق event ويرجع tracking URL كمان. الاستيرادات موجودة في المصدر.

public function store(StoreOrderRequest $request, OrderCreator $creator): JsonResponse
{
    $data = $request->validated();
    if ($data['payment_method'] === 'card') {
        return response()->json(['message' => 'Use the card endpoint.'], 422);
    }
    $order = $creator->create($data, $request->user(), Order::STATUS_NEW);
    return response()->json(['order' => $order], 201);
}

كل سطر بيعمل إيه؟

  • public function store(...): method معالجة إنشاء الطلب. الاسم نفسه اختيارنا، والـ route هي اللي بتوصله بالـ URL.
  • StoreOrderRequest $request: Laravel يجهّز طلبًا متحققًا منه باستخدام قواعد Form Request قبل دخول method إذا نجح authorization والـ validation.
  • OrderCreator $creator: dependency injection؛ Laravel يجهّز object من الخدمة ويمرّره. : JsonResponse نوع الاستجابة.
  • $data = $request->validated(): هات نتيجة التحقق بدل الاعتماد على كل input من غير تمييز.
  • if (... === 'card'): لو العميل اختار كارت، ما تنشئش الطلب هنا كأنه كاش. === مقارنة صارمة.
  • return response()->json(..., 422): ارجع خطأ من هذا المثال واقفل المسار. => يربط اسم المفتاح بقيمته في PHP array.
  • } يقفل شرط الكارت.
  • $creator->create(...): ابعت البيانات، المستخدم الحالي أو null للضيف، وحالة new إلى الخدمة المشتركة. Order::STATUS_NEW ثابت من الـ model يقلل أخطاء الكتابة.
  • آخر return: ارجع الطلب JSON بكود201 لإنشاء مورد جديد. } يقفل method.

الخدمة الأصلية OrderCreator تنفّذ تحقق التوفر والسعر والحفظ؛ بيستخدمها cash controller وpayment controller بدل تكرار نفس القواعد. ده فصل مسؤوليات، مش شرط إن كل controller صغير يحتاج service من أول يوم.

نفّذ بإيدك: امشِ على المثال مرة بقيمة cash ومرة card، وحدد هل create تتنادى. ما تحتاجش تنشئ طلبًا جديدًا فعلًا.

المتوقع: cash يصل للخدمة ويرجع201 إذا نجح الحفظ؛ card يتوقف عند422 في المثال.

غلطة شائعة: تسمح لمسار الكاش ينشئ طلب card بحالة new قبل التحقق من الدفع؛ الموظف ممكن يبدأ تجهيزه وهو غير مدفوع.

سؤال إنترفيو: إيه الفرق بين controller وservice؟

Controller يتعامل مع سياق HTTP وينسّق الرد. Service تجمع منطق العمل القابل لإعادة الاستخدام، مثل إنشاء طلب بأسعار موثوقة. Laravel مش بيفرض service layer لكل عملية.

3. إزاي تتحقق من بيانات عناصر جاية جوه array؟

مثال مبسّط من StoreOrderRequest.php. ده جزء من قواعده فقط؛ متحذفش قواعد العميل والعنوان ونوع الطلب وباقي قواعد المصدر.

public function rules(): array
{
    return [
        'branch_id' => ['required', 'integer', 'exists:branches,id'],
        'items' => ['required', 'array', 'min:1'],
        'items.*.menu_item_id' => ['required', 'integer', 'exists:menu_items,id'],
        'items.*.quantity' => ['required', 'integer', 'min:1', 'max:20'],
        'items.*.notes' => ['nullable', 'string', 'max:200'],
    ];
}

كل سطر بيعمل إيه؟

  • public function rules(): array: Laravel يقرأ من الدالة دي قائمة validation rules. array نوع الناتج.
  • return [: ابدأ الـ array اللي كل مفتاح فيها اسم field وكل قيمة قواعده.
  • branch_id: إجباري، integer، ولازم القيمة موجودة في عمود id بجدول branches. وجود الفرع غير كونه فعّالًا؛ الخدمة بتتحقق من فعاليته لاحقًا.
  • items: لازم قائمة، وبها عنصر واحد على الأقل. هنا min:1 حد لحجم الـ array، مش حد لسعرها.
  • items.*.menu_item_id: النقطة للوصول داخل البنية، و* معناها كل عنصر. يتحقق من معرف كل منتج ومن وجوده في جدول المنيو.
  • items.*.quantity: كل كمية عدد صحيح من1 إلى20. الصفر أو25 غير مقبولين.
  • items.*.notes: الملاحظة ممكن تكون null؛ لو فيها قيمة فلازم نص لحد200 حرف. دي قاعدة خلفية حتى لو input الواجهة عليها maxLength.
  • ]; يقفل array؛ } يقفل الدالة.

لو طلب JSON فشل في القواعد، Laravel عادة يرجع422 مع errors بدل الدخول لـ controller. الـ request الفعلي فيه authorize() يرجعtrue للسماح بضيف يعمل checkout؛ ده مش معناه إن باقي endpoints مفتوحة أو إن أي input صالح. قواعد pickup الإضافية تستخدم وقت التحضير من AppSetting ثم fallback config. حقل opening_hours الحالي نص للعرض؛ الكود الإضافي بيفحص opens_at/closes_at غير الموجودين حاليًا، فمتقولش إن عندنا تحقق ساعات تشغيل كامل.

نفّذ بإيدك: على الورق، اكتب payload بعنصر واحد quantity=0 ثم quantity=2. حدّد اسم مفتاح الخطأ المتوقع للأول.

المتوقع: الأول يرفض الكمية، ومفتاح الخطأ items.0.quantity؛ الثاني يعدي القاعدة دي لو باقي الشروط سليمة.

غلطة شائعة: تعتبر exists:menu_items,id ضمان إن المنتج متاح بالفرع. ده تحقق إضافي في الخدمة، مش في القاعدة دي.

سؤال إنترفيو: ليه نعمل validation في السيرفر لو الفرونت بالفعل بيتحقق؟

لأن العميل يقدر يتجاوز الواجهة أو يعدل request. تحقق الواجهة لتحسين التجربة؛ تحقق السيرفر لحماية قواعد النظام والبيانات.

4. لو تحديث الحالة نجح وتسجيل التاريخ فشل، نعمل إيه؟

مثال مبسّط من StaffOrderController.php. داخل method عندها $order و$data؛ نفترض authorization والتحقق من الانتقال تمّا بالفعل. الأصل يعيد قراءة الطلب تحت lock، ويفحص expected_status ويسجل المستخدم والسبب كمان.

DB::transaction(function () use ($order, $data) {
    $from = $order->status;
    $order->update(['status' => $data['status']]);
    OrderStatusLog::create([
        'order_id' => $order->id,
        'from_status' => $from,
        'to_status' => $data['status'],

كل سطر بيعمل إيه؟

  • DB::transaction(...): اجمع تغييرات قاعدة البيانات داخل transaction؛ لو callback فشل بـ exception تتعمل rollback لتغييراتها.
  • function () use ($order, $data): دالة من غير arguments مباشرة؛ use هنا تدخل المتغيرات الخارجية إلى نطاق closure. دي غير use استيراد class أعلى الملف.
  • $from = $order->status: احتفظ بالحالة القديمة قبل تعديلها.
  • $order->update(...): حدّث الصف. الـ array تحدد اسم الحقل والقيمة الجديدة.
  • OrderStatusLog::create([: أضف سجلًا جديدًا من خلال model.
  • order_id: الطلب اللي حصل عليه التغيير.
  • from_status: الحالة القديمة، وto_status: الحالة الجديدة من البيانات المتحقق منها.
  • created_at => now(): وقت التغيير الحالي.
  • ]); يقفل بيانات التاريخ واستدعاء create؛ }); يقفل transaction callback والاستدعاء.

لو إنشاء التاريخ فشل، تعديل الحالة اللي سبقه ما يتثبتش وحده. نجاح transaction مش معناه إنها تمنع كل تداخل تلقائيًا؛ النسخة الفعلية تستخدم lockForUpdate()->findOrFail(...) داخلها، وتقارن expected_status علشان ترفض تعديل موظف مبني على حالة قديمة بكود409. الـ locking يعتمد على قاعدة البيانات: SQLite مش بتوفر نفس row-level FOR UPDATE في MySQL/PostgreSQL، فاختبار بسيط عليها مش إثبات لسلوك التزامن في محرك الإنتاج. ده جزء مهم مش موجود في المثال المصغّر، فلا تستبدله بالأصل.

نفّذ بإيدك: حط علامة على كل سطر يغيّر DB، وافترض إن إضافة التاريخ رمت exception. اكتب النتيجة المطلوبة للحالة والتاريخ. التمرين على الورق أو في اختبار معزول، مش بإفساد قاعدة حقيقية.

المتوقع: مفيش تحديث حالة منفرد بدون سجله؛ تغييرات callback تتراجع معًا.

غلطة شائعة: تفترض transaction ترجع طلب HTTP خارجي لـ Stripe أو إيميل اتبعت. rollback تخص تغييرات DB المشاركة؛ الأنظمة الخارجية تحتاج تصميم تعويض/إعادة محاولة مناسب.

سؤال إنترفيو: الفرق بين transaction وrow lock؟

Transaction تجمع عمليات كوحدة نجاح/فشل. Row lock ينظم وصول معاملات متزامنة لصفوف معينة حسب قاعدة البيانات. الأول وحده مش ضمان ضد كل race condition.

5. Laravel عرف يجيب StripePaymentGateway منين؟

مقتطف فعلي من AppServiceProvider.php. الأسماء مستوردة فوق، وprovider مسجل في bootstrap/providers.php.

public function register(): void
{

}

كل سطر بيعمل إيه؟

  • public function register(): دالة lifecycle للـ service provider علشان تسجل الاعتماديات. مش registration لحساب مستخدم.
  • : void: مش بنرجع بيانات مقصودة من الدالة.
  • {: بداية جسم الدالة.
  • $this: الـ provider الحالي.
  • ->app: Laravel service container؛ المسؤول عن تجهيز الاعتماديات وحلها.
  • ->bind(A, B): لما الكود يطلب A، استخدم B كالتنفيذ المسجل.
  • PaymentGateway::class: اسم interface في app/Contracts/PaymentGateway.php، بتحدد methods مطلوبة مثل createIntent وparseWebhook.
  • StripePaymentGateway::class: الـ class اللي بتنّفذ العقد ده فعلًا عن طريق Stripe SDK.
  • ; نهاية التعليمة، و} نهاية register.

علشان كده PaymentController يقدر يطلب parameter نوعه PaymentGateway بدل ما يعمل new StripePaymentGateway بنفسه. لو غيرت بوابة الدفع، تقدر تبدّل التنفيذ مع الاحتفاظ بعقد مناسب؛ لكن بوابتين مختلفتين مش شرط يتطابقوا من غير أي تعديل تصميمي. الـ interface لا تحتوي أسرار Stripe؛ الإعدادات الخاصة تقرأ على السيرفر.

ده مفيد للاختبارات كمان: الاختبار يقدر يسجل fake gateway بدل الحقيقي، فيجرّب منطق webhook من غير اتصال أو فلوس. وجود اختبار ببوابة fake مش دليل إن الاتصال بـ Stripe الحقيقي اتجرّب؛ ده نطاق اختبار مختلف.

نفّذ بإيدك: افتح signature بتاع PaymentController::createIntent وشاور على parameter اللي Laravel هيحلّه باستخدام التسجيل ده. ثم افتح test الدفع وشوف instance(PaymentGateway::class, $gateway).

المتوقع: تلاقي $gateway مع نوع PaymentGateway، وتلاقي اختبار يستبدل التنفيذ بشكل صريح من غير تعديل controller.

غلطة شائعة: تفتكر interface وحدها تعمل object، أو تكتب مفاتيح Stripe الخاصة داخل React أو ملف توثيق.

05 — أسئلة وأمثلة: قاعدة البيانات وEloquent

ذاكر مثال واحد كل مرة. المقتطفات للتفسير؛ مش تعليمات لحذف قاعدة بياناتك أو تشغيل migrations عشوائيًا. لا تستخدم migrate:fresh على مشروع عليه بيانات عايز تحتفظ بيها.

تصحيح مهم: الكود يدعم MySQL وSQLite حسب إعداد الاتصال، مش معنى وجود database.sqlite إنه المستخدم حاليًا. config/database.php يقرأ DB_CONNECTION، والـ fallback فيه sqlite. اختبارات المشروع تضبط SQLite مؤقتة في الذاكرة عبر phpunit.xml. مش محتاج تفتح أو تشارك .env علشان تذاكر الأمثلة.

1. يعني إيه migration، وإزاي تمنع تكرار نفس المنتج في نفس الفرع؟

مقتطف فعلي داخل up() في migration جدول branch_menu_item. الاستيرادات Schema وBlueprint موجودة أعلى الملف؛ متشغّلوش كـ PHP مستقل.

Schema::create('branch_menu_item', function (Blueprint $table) {
    $table->id();
    $table->foreignId('branch_id')->constrained()->cascadeOnDelete();
    $table->foreignId('menu_item_id')->constrained()->cascadeOnDelete();
    $table->decimal('price', 10, 2);
    $table->boolean('is_available')->default(true);
    $table->timestamps();

    $table->unique(['branch_id', 'menu_item_id']);
});

كل سطر بيعمل إيه؟

  • Schema::create: إنشاء جدول جديد بالاسم المحدد. :: استدعاء على facade؛ مش إضافة صف منتج.
  • function (Blueprint $table): دالة تستقبل أداة وصف الأعمدة. { بداية تعليمات إنشاء الجدول.
  • $table->id(): عمود معرّف أساسي للصف. $ لمتغير PHP و-> للوصول إلى method على object.
  • foreignId('branch_id'): عمود بيربط الصف بالفرع. constrained() يضيف قيد مرجعي للجدول المستنتج من الاسم.
  • cascadeOnDelete(): حذف الفرع يؤدي لحذف صفوف الربط التابعة له. نفس الفكرة للسطر الخاص بـ menu_item_id.
  • decimal('price', 10, 2): رقم عشري دقيق، إجمالي أرقامه 10، منها رقمين بعد العلامة؛ مش 10 قبلها و2 بعدها.
  • boolean(...)->default(true): متاح افتراضيًا لو الإدخال ما حددش قيمة.
  • timestamps(): إضافة created_at وupdated_at.
  • unique(['branch_id', 'menu_item_id']): امنع تكرار نفس الزوج؛ مش معناه إن المنتج ممنوع يكون في فرع تاني.
  • });: اقفل الدالة واستدعاء الإنشاء.

الـ migration توثيق قابل للتنفيذ لتغيير الهيكل. up يطبق التغيير، وdown في المصدر يحذف الجدول عند rollback؛ rollback ممكن يفقد بيانات، فمش تجربة بريئة على قاعدة حقيقية.

نفّذ بإيدك: اكتب ثلاث أزواج: (1, 7) و(2, 7) و(1, 7)، وحدد أي صف يتعارض مع القيد.

المتوقع: الأول والتاني مختلفين؛ الثالث مكرر للأول ومرفوض.

غلطة شائعة: تعمل unique على menu_item_id وحده فتمنع المنتج من الظهور في أكثر من فرع، أو تعتمد على فحص JavaScript لمنع التكرار في قاعدة البيانات.

سؤال إنترفيو: الفرق بين migration وmodel؟

Migration تغيّر هيكل قاعدة البيانات. Model يتيح التعامل مع صفوفها وعلاقاتها من PHP. كتابة علاقة في model وحدها لا تنشئ foreign key في قاعدة البيانات.

2. الطلب الواحد فيه منتجات كتير؛ بنكتب العلاقة إزاي؟

مقتطف فعلي من Order.php. الدالة مكتوبة داخل class Order وHasMany مستوردة فوق.

public function items(): HasMany
{
    return $this->hasMany(OrderItem::class);
}

كل سطر بيعمل إيه؟

  • public: متاحة للكود اللي يتعامل مع Order، مش مقتصرة على نفس class.
  • function items(): تعريف دالة علاقة اسمها items من اختيارنا. الأقواس فاضية لأن العلاقة مش محتاجة parameter هنا.
  • : HasMany: نوع الـ object اللي الدالة ترجعّه: وصف علاقة واحد إلى متعدد، مش array منتجات جاهزة.
  • {: بداية جسم الدالة.
  • return: رجّع وصف العلاقة للمتصل.
  • $this: الطلب الحالي؛ instance من model Order.
  • ->hasMany(...): الطلب الحالي له صفوف متعددة في model آخر.
  • OrderItem::class: اسم class الكامل الخاص ببند الطلب. مش استدعاء لبناء منتج جديد.
  • }: نهاية الدالة.

Laravel يستنتج إن order_items.order_id بيربط البنود بالطلب. العلاقة العكسية موجودة باسم order() داخل OrderItem.php وبتستخدم belongsTo.

في PHP فيه فرق بين $order->items()، اللي بيرجع relation تقدر تضيف عليه query، و$order->items، اللي بيرجع مجموعة البنود ويحمّلها لو محتاج. وفي OrderCreator بنستخدم العلاقة لإنشاء بند؛ Laravel يربط order_id بالطلب الحالي.

الـ model كمان فيه $fillable لتحديد الحقول المسموح ملؤها جماعيًا. دي مش validation ولا صلاحيات؛ لازم server validation قبل إدخال بيانات العميل. الـ casts تحول تمثيل بعض القيم، مثل total_price إلى decimal بموضعين وpickup_time إلى تاريخ.

نفّذ بإيدك: على الورق، ارسم Order رقم 10 وبندين order_id بتاعهم 10 وبند order_id بتاعه 11. حدّد البنود اللي هتظهر للطلب 10. قراءة المشروع تكفي؛ متضيفش طلبات حقيقية.

المتوقع: أول بندين بس، مش كل منتجات المنيو.

غلطة شائعة: تخلط بين MenuItem، المنتج في الكتالوج، وOrderItem، بند شراء له كمية وسعر تاريخي.

سؤال إنترفيو: ليه OrderItem يحتفظ بسعره واسمه؟

لأن سعر واسم المنيو ممكن يتغيروا لاحقًا. price وitem_name داخل بند الطلب بيمثلوا snapshot وقت الشراء، بدل تغيير تاريخ الفواتير مع تعديل الكتالوج.

3. نفس البيتزا سعرها مختلف حسب الفرع؛ نخزّن ده فين؟

مقتطف فعلي من Branch.php. جدول الربط من السؤال الأول هو اللي بيخزن السعر والتوفر لكل زوج فرع/منتج.

public function menuItems(): BelongsToMany
{
    return $this->belongsToMany(MenuItem::class)
        ->withPivot(['price', 'is_available'])
        ->withTimestamps();
}

كل سطر بيعمل إيه؟

  • public function menuItems(): دالة العلاقة اللي نطلب منها منتجات الفرع.
  • : BelongsToMany: نوع علاقة many-to-many. الفرع عنده منتجات كتير، ونفس المنتج موجود في فروع كتير.
  • return $this->belongsToMany(MenuItem::class): عرّف الطرف التاني للعلاقة. Laravel يستنتج جدول الربط branch_menu_item من الاسمين.
  • ->withPivot(['price', 'is_available']): لما تحمل المنتجات، حمّل معاها الحقلين دول من صف الربط، مش من جدول menu_items.
  • ->withTimestamps(): خلي العلاقة تدير حقول وقت الإنشاء والتحديث في جدول الربط عند عمليات العلاقة المناسبة.
  • ;: نهاية سلسلة الاستدعاءات، و} نهاية الدالة.

-> هنا بيتكرر لأن كل method بيرجع object يسمح بالاستدعاء اللي بعده؛ دي method chaining. withPivot مش اللي أنشأ الأعمدة؛ إنشاء الأعمدة حصل في migration.

في الاستخدام تقدر تقرأ $item->pivot->price عند تحميل المنتج عن طريق العلاقة. API المنيو الحالي يحول البيانات إلى branch_options؛ كل خيار فيه branch_id وprice وis_available. مفيش سعر موحد مفروض على كل الفروع، والـ endpoint الحالي يرجّع الفروع الفعّالة بدل افتراض فلتر branch query قديم.

نفّذ بإيدك: اكتب بيانات افتراضية لنفس المنتج 7: سعره 190 في الفرع 1 و210 في الفرع 2. حدّد القيم اللي تتخزن في menu_items والقيم اللي تتخزن في pivot.

المتوقع: الاسم والوصف في menu_items، والسعر والتوفر في صف منفصل لكل فرع داخل pivot.

غلطة شائعة: تستخدم $item->price وتنسى إن السعر في هذا التصميم خاص بالـ pivot، أو تعدّل سعر الطلب القديم بمجرد تغيّر سعر المنيو.

سؤال إنترفيو: إمتى علاقة many-to-many تحتاج حقول زيادة في pivot؟

لما البيانات تخص العلاقة نفسها، مش أي طرف وحده؛ زي سعر المنتج وتوفره داخل فرع معين. نفس الفكرة ممكن تطبق على دور مستخدم داخل مشروع معين.

4. يعني إيه N+1، وإزاي with بتساعد؟

مثال مبسّط من MenuController.php. الأصل بيحمّل الفروع ويطبّق فلاتر إضافية؛ هنا ركّز على تحميل category فقط. الكود داخل method بعد استيراد MenuItem.

$items = MenuItem::query()
    ->where('is_active', true)
    ->with('category')
    ->get();
foreach ($items as $item) {
    echo $item->category?->name;
}

كل سطر بيعمل إيه؟

  • $items = MenuItem::query(): ابدأ query builder للمنتجات. لسه ما قريناش كل الصفوف.
  • ->where('is_active', true): ضيف شرط المنتجات الفعّالة. ده اختصار تعليمي؛ الأصل بيشترط كمان category فعّالة.
  • ->with('category'): اطلب تحميل التصنيفات المطلوبة بشكل مجمّع بدل query منفصل لكل منتج عند قراءتها.
  • ->get(): نفّذ الاستعلام وارجع Collection من models؛ هنا التنفيذ الفعلي للقراءة.
  • foreach ($items as $item): مر على كل منتج. $item هو العنصر الحالي، زي متغير العنصر في v-for وmap.
  • echo: اطبع اسم التصنيف للتوضيح فقط؛ الـ API الفعلي بيرجع JSON بدل طباعة متناثرة.
  • $item->category?->name: اقرأ اسم العلاقة لو موجودة. ?-> null-safe access؛ يمنع قراءة الخاصية على null.
  • }: اقفل التكرار.

بدون eager loading، 20 منتج ممكن ينتج عنهم query للمنتجات وقراءات تصنيف إضافية مع الوصول للعلاقات؛ دي فكرة N+1. مع with غالبًا query للمنتجات وواحد للتصنيفات في علاقة belongsTo دي؛ مش بالضرورة JOIN واحد، ومش قاعدة إن أي with يعني استعلامين فقط لكل تصميم.

نفّذ بإيدك: علّم على السطر اللي بينفّذ query فعلًا، وبعدها اشرح إيه المتوقع يتغيّر لو شلت with مع استمرار قراءة category داخل الحلقة. ما تحتاجش تعدّل production.

المتوقع: get ينفّذ؛ حذف التحميل المسبق ممكن يزيد queries حسب البيانات وطريقة الوصول.

غلطة شائعة: تقول إن with تحوّل العلاقات تلقائيًا إلى SQL JOIN أو تمنع كل مشاكل الأداء، حتى لو لسه عندك query جوه حلقة في مكان آخر زي حساب بنود الطلب. وفي الأمان: Eloquent/query builder يربط قيم where كـ parameters بدل دمجها داخل SQL؛ ده يساعد ضد SQL injection للقيم، لكنه مش ضمان أمان أي raw SQL تكتبه. متجمعش input مستخدم داخل DB::raw، وأسماء الأعمدة/اتجاه الترتيب القادمة من العميل تحتاج allowlist؛ مش كل جزء من SQL قابل للـ parameter binding.

سؤال إنترفيو: إزاي تكتشف N+1؟

تراقب عدد وشكل queries أثناء طلب واحد بأدوات مناسبة للتطوير أو query logging آمن، وتشوف هل نفس نوع الاستعلام بيتكرر لكل عنصر. بعدين تستخدم eager loading أو batch query حسب الحالة.

5. الفرق بين Seeder وFactory وإزاي أعمل بيانات تدريب من غير لمس الحقيقي؟

مثال تدريبي إضافي مبني على UserFactory.php ونمط اختبارات OrderOperationsTest.php. اكتبه داخل feature test له RefreshDatabase وفي بيئة testing معزولة فقط، مش Tinker على قاعدة شغلك.

$user = User::factory()->make([
    'name' => 'Practice User',
    'role' => 'customer',
]);
$this->assertSame('customer', $user->role);
$this->assertFalse($user->exists);

كل سطر بيعمل إيه؟

  • User::factory(): هات مصنع بيانات وهمية للـ User. User لازم تكون مستوردة في ملف الاختبار.
  • ->make([: كوّن model في الذاكرة بالقيم الافتراضية للمصنع مع التعديلات دي؛ ما تحفظوش في قاعدة البيانات.
  • 'name' => 'Practice User': بدّل الاسم المولّد باسم واضح للتدريب.
  • 'role' => 'customer': حدّد الدور بدل الاعتماد على default من غير ما تفهمه.
  • ]);: اقفل تعديلات الـ factory واستدعاء make.
  • $this->assertSame(...): assertion من PHPUnit؛ اتأكد إن القيمة والنوع هما المتوقعين.
  • $this->assertFalse($user->exists): اتأكد إن model لسه مش محفوظ. دي property على Eloquent، مش فحص لوجود الحساب في كل قواعد البيانات.

create() بدل make() تحفظ صفًا؛ متبدّلهمش على قاعدة حقيقية من غير قصد. Factory بتجهّز بيانات متنوعة للاختبارات، وSeeder بينظم تجهيز بيانات بداية/عرض للتطبيق وغالبًا بيكتب في قاعدة البيانات. الاتنين ممكن يستخدموا بعض، فمش الفرق إن واحد عشوائي دائمًا والتاني ثابت دائمًا.

المصدر الحالي DatabaseSeeder.php بينادي MenuCatalogSeeder ثم StaffUserSeeder ثم DemoOrderSeeder. لا تشغّل seeders افتراضيًا على production، ولا تستخدم بيانات دخول الديمو لحساب حقيقي. مش مطلوب تنسخ أي كلمة سر للتعلّم.

نفّذ بإيدك: اكتب المثال داخل اختبار منفصل آمن، أو توقّع ناتجه على الورق لو لسه مش مجهّز بيئة اختبارات. إعدادات المشروع للاختبار تشير إلى sqlite :memory:؛ تحقق من عدم وجود override قبل أي تشغيل.

المتوقع: الاختباران ينجحوا، وmake نفسها لا تضيف مستخدمًا إلى قاعدة البيانات.

غلطة شائعة: تشغّل migrate:fresh --seed على القاعدة اللي فيها طلباتك، أو تعتبر بيانات factory بيانات إنتاج صالحة.

سؤال إنترفيو: ليه نفصل بيانات الاختبار عن قاعدة التطوير؟

علشان النتائج تكون قابلة للتكرار من غير اعتماد على طلباتك الشخصية، وعلشان عمليات التنظيف أو إعادة بناء الجداول في الاختبارات ما تمسحش بياناتك الفعلية.

04 — أسئلة وأمثلة: تسجيل الدخول والصلاحيات

خد سؤال واحد بس في كل مرة: اكتب الكود بإيدك، اشرح السطور بصوتك، وبعدها افتح إجابة الإنترفيو. الأمثلة مقتطفات للتعلّم؛ متستبدلش بيها الملفات الكاملة.

الشرح هنا لنسخة Pizza CRM اللي بتشتغل بـ Laravel. لو VITE_DEMO_MODE مفعّل، csrfFetch بيحوّل الطلبات لمحاكاة في المتصفح؛ نجاح تسجيل الدخول في الديمو مش دليل على تشغيل السيرفر أو أمانه. AutoCare الحالي ديمو متصفح من غير نظام دخول backend مماثل.

1. ليه طلب تسجيل الدخول محتاج CSRF token وكوكيز؟

مثال مبسّط من resources/js/lib/api.js. اكتبه في ورقة أو ملف تدريب؛ مش بديل للدالة الأصلية، اللي كمان بتعالج الأخطاء وJSON وFormData.

const token = document.querySelector('meta[name="csrf-token"]')?.content;
const response = await fetch('/api/auth/login', {
    method: 'POST',
    credentials: 'same-origin',
    headers: {
        Accept: 'application/json',
        'Content-Type': 'application/json',
        'X-CSRF-TOKEN': token,
    },
    body: JSON.stringify(credentials),
});

كل سطر بيعمل إيه؟

  • const token: متغير لقيمة الرمز. document.querySelector(...) يجيب عنصر الـ meta، و?.content يقرأ قيمته لو العنصر موجود؛ مش هو رمز تسجيل الدخول.
  • const response = await fetch(...): ابعت HTTP request واستنى الرد. await لازم يكون داخل دالة async أو بيئة تدعم top-level await. credentials في آخر المثال object موجود مسبقًا فيه email وpassword.
  • method: 'POST': العملية بتغيّر حالة تسجيل الدخول، مش مجرد قراءة.
  • credentials: 'same-origin': اسم إعداد fetch، مش object بيانات الدخول؛ يسمح بإرسال كوكيز نفس الموقع. ده أصلًا default fetch المعتاد، وكتابته هنا توضيح للقصد.
  • headers: { ... }: معلومات عن الطلب. Accept يطلب رد JSON؛ Content-Type يصف الجسم المرسل.
  • 'X-CSRF-TOKEN': token: ابعت الرمز اللي Laravel ولّده للصفحة. دوره مقاومة CSRF، مش إثبات إن المستخدم admin.
  • body: JSON.stringify(credentials): حوّل object بيانات الدخول لنص JSON. }); يقفل إعدادات fetch وينهي التعليمة.

نفّذ بإيدك: افتح Network في أدوات المتصفح وسجّل الدخول بحساب تجريبي محلي. شوف Method وRequest Headers من غير ما تنسخ كلمة السر أو الكوكيز في ملفات المذاكرة.

المتوقع: POST للـ endpoint، CSRF header، وبعد النجاح session cookie يعرّف المتصفح عند الطلبات التالية. عدم وجود token صحيح ممكن ينتج عنه 419؛ الـ helper الأصلي بيحدّث الرمز لما السيرفر يرجّع رمزًا جديدًا.

غلطة شائعة: تفتكر CSRF token بديل لكلمة السر أو تتوقع إن الكوكي تحتوي على كلمة السر. كمان fetch مش بيرمي خطأ تلقائيًا لكل 401/422؛ لازم فحص response.ok كما في الـ helper الأصلي.

سؤال إنترفيو: هل CSRF وAuthentication نفس الحاجة؟

لأ. Authentication يحدد مين المستخدم. CSRF protection بيحاول يمنع موقعًا آخر من تنفيذ عمليات باستخدام جلسة المستخدم من غير قصده. الـ session cookie والـ CSRF token لكل واحد دور مختلف.

2. إزاي Laravel يتأكد من الباسورد ويبدأ جلسة آمنة؟

مثال مبسّط من AuthController.php. المقطع داخل login؛ $credentials ناتجة من validation، و$remember قيمة Boolean. اختصرنا رسالة الخطأ وفصلنا فحص الحساب المعطّل؛ الملف الأصلي بيعمل الفحص ده كمان.

if (! Auth::attempt($credentials, $remember)) {
    throw ValidationException::withMessages([
        'email' => ['The provided credentials are incorrect.'],
    ]);
}
$request->session()->regenerate();
return response()->json(['user' => $request->user()]);

كل سطر بيعمل إيه؟

  • if (...): نفّذ اللي بين الأقواس المعقوفة لو الشرط صحيح.
  • Auth::attempt(...): اطلب من Laravel التحقق من بيانات الدخول باستخدام الـ guard. :: وصول لدالة على الـ facade، و$ بداية اسم متغير PHP.
  • !: اعكس النتيجة؛ ندخل فرع الخطأ لما محاولة الدخول تفشل. Laravel يقارن كلمة السر بالـ hash، مش بمقارنة نصين عاديين منك.
  • throw: أوقف المسار الحالي وارمِ exception. ValidationException::withMessages يجهّز خطأ validation، وعند طلب JSON يكون غالبًا 422.
  • 'email' => [...]: اسم الحقل ورسائله. => تربط المفتاح بالقيمة داخل array PHP.
  • ]); يقفل قائمة الرسائل والاستدعاء، و} يقفل شرط الفشل.
  • $request->session()->regenerate(): بعد النجاح غيّر session ID لتقليل خطر session fixation. -> وصول لدالة/خاصية على object.
  • return response()->json(...): رجّع المستخدم الحالي بصيغة JSON. في الملف الفعلي الرد كمان فيه رسالة وCSRF token جديد وعلاقة الفرع.

المشروع بيستخدم session guard من config/auth.php، مش JWT ولا Sanctum SPA بمجرد وجود مسار يبدأ بـ /api.

نفّذ بإيدك: تتبّع فرعين على الورق: باسورد غلط، وباسورد صحيح لحساب فعّال. حدّد هل سطر regenerate هيتنفّذ في كل فرع.

المتوقع: الغلط يقف عند exception؛ النجاح يكمل ويعيد توليد الجلسة. الكود الفعلي يرفض الحساب غير الفعّال حتى لو كلمة السر صحيحة.

غلطة شائعة: تخزّن user في React وتعتبر ده تسجيل دخول حقيقي. الحالة دي عرض للواجهة؛ Laravel هو اللي بيثبت هوية الطلبات. عند logout، الأصل بيعمل logout() ثم invalidate() ثم regenerateToken()؛ مسح user من React وحده مش كفاية.

سؤال إنترفيو: ليه نغيّر session ID بعد الدخول؟

علشان مهاجم ما يستغلش session ID قديم يعرفه أو ثبّته قبل تسجيل الدخول. ده دفاع ضد session fixation، مش تشفير للباسورد.

3. الباسورد بيتخزّن إزاي، وليه مش بيرجع في JSON؟

مثال مبسّط من User.php، اختصرنا القوائم للخصائص المتعلقة بالسؤال. السطور دي مكانها داخل class الـ model، مش ملف PHP مستقل.

protected $hidden = ['password', 'remember_token'];
protected function casts(): array
{
    return [
        'password' => 'hashed',
        'is_active' => 'boolean',
    ];
}

كل سطر بيعمل إيه؟

  • protected $hidden: إعداد داخل model يحدد خصائص لا تُضمّن في التحويل العادي إلى array/JSON. protected مستوى الوصول للخاصية، مش تشفير للبيانات.
  • ['password', 'remember_token']: أسماء الأعمدة المطلوب استبعادها. الـ password hash نفسه بيانات حساسة ومش محتاج يرجع للواجهة.
  • protected function casts(): array: دالة إعدادات اسمها casts. الأقواس () معناها مفيش arguments هنا، و: array نوع القيمة اللي الدالة هترجعها.
  • {: بداية جسم الدالة.
  • return [: رجّع array من أسماء الخصائص وطريقة التعامل معاها.
  • 'password' => 'hashed': لما تسند باسورد جديد من خلال model، Laravel يتعامل مع تخزينه كـ hash. ما تشيلش ده وتكتب الباسورد raw.
  • 'is_active' => 'boolean': لما تتعامل مع القيمة في model، تحصل على true/false بدل اختلاف تمثيل قاعدة البيانات.
  • ]; يقفل array وينهي return، و} يقفل الدالة.

الـ hidden لا يمنع مطوّرًا من كتابة response يدوي يسرّب القيمة، ولا يمنع تعديلها. وفي نفس الملف $fillable يحدد حقول mass assignment المسموحة؛ هو شيء مختلف تمامًا. التسجيل الفعلي يمرّر validated data فيها name/email/password فقط، مش role جاية من العميل.

نفّذ بإيدك: اقرأ payload استجابة الدخول في Network على النسخة المحلية. ابحث عن اسم المستخدم وrole، واتأكد إن password وremember_token مش موجودين. ما تطبعش hash حقيقي علشان تثبت الفكرة.

المتوقع: بيانات عرض المستخدم موجودة، كلمة السر والـ hash مش ضمن JSON.

غلطة شائعة: تفتكر إن $hidden يحمي الحقل من التعديل، أو إن hashed تشفير تقدر تعكسه علشان ترجع كلمة السر. الـ hash للتحقق، مش للاسترجاع.

سؤال إنترفيو: الفرق بين hashing وencryption؟

Encryption قابل للفك بالمفتاح المناسب. Password hashing مصمم للتحقق من كلمة السر من غير استرجاع أصلها؛ Laravel بيوفر أدوات للمقارنة الآمنة بدل تنفيذها بنفسك.

4. هل إخفاء زر Staff من الواجهة يعتبر صلاحيات؟

لأ. مقتطف فعلي من RequireRole.php. الـ middleware متسجل باسم role في bootstrap/app.php.

public function handle(Request $request, Closure $next, string ...$roles): Response
{
    $user = $request->user();
    abort_unless($user && $user->is_active && in_array($user->role, $roles, true), 403);
    abort_if($user->role === 'staff' && ! $user->branch_id, 403, 'This staff account is not assigned to a branch.');

    return $next($request);
}

كل سطر بيعمل إيه؟

  • public function handle: نقطة معالجة الـ middleware. public يسمح باستدعائها من Laravel.
  • Request $request: object الطلب؛ Closure $next الدالة اللي تكمل المعالجة؛ string ...$roles تجمع بقية الـ role arguments في array. : Response نوع الرد المتوقع.
  • $user = $request->user(): هات المستخدم الحالي من الجلسة، مش من body أرسله الزائر.
  • abort_unless(..., 403): أوقف الطلب إلا لو الشرط متحقق. && معناها لازم كل الشروط صح. التقييم يقف لو مفيش user بدل محاولة قراءة خصائص null.
  • $user->is_active: الحساب لازم يكون فعّالًا. in_array(..., true) يتأكد إن الدور ضمن الأدوار المسموحة بمقارنة صارمة للنوع.
  • abort_if(...): الموظف اللي ملوش فرع مربوط بيه يتمنع. === مقارنة صارمة، و! معناها عدم وجود قيمة branch صالحة هنا.
  • return $next($request): لو الشروط نجحت، كمّل إلى المعالجة التالية. القوس الأخير يقفل الدالة.

مسارات الموظفين تجمع auth مع role:staff,admin، ومسارات الإدارة تستخدم role:admin. إخفاء زر في React تحسين للواجهة، مش حماية endpoint.

نفّذ بإيدك: اكتب نتائج ثلاثة أمثلة على الورق: customer فعّال؛ staff فعّال له فرع؛ staff فعّال من غير فرع. افترض قائمة الأدوار staff/admin.

المتوقع: الأول 403، الثاني يكمل، الثالث 403. الزائر أصلًا بيتوقف عند auth middleware قبل ده في مجموعة الموظفين.

غلطة شائعة: تبعت role من المتصفح وتعتمد عليها، أو تكتفي بإن الرابط مش ظاهر.

سؤال إنترفيو: الفرق بين 401 و403؟

401 يعني الطلب مش مثبت هوية مستخدم مقبول. 403 يعني الوصول ممنوع؛ مثل عميل مسجل بيحاول يستخدم إجراء موظف. اختيار الكود الفعلي يعتمد على مسار الحماية وسياق الاستجابة.

5. الموظف شغال في فرع واحد؛ إيه اللي يمنعه يشوف طلب فرع تاني؟

مقتطف فعلي من StaffOrderController.php. الدالة داخل الـ controller، وبتتنده قبل عرض طلب واحد أو تغيير حالته.

private function authorizeBranch(Request $request, Order $order): void
{
    $user = $request->user();
    abort_unless($user->isAdmin() || (int) $user->branch_id === (int) $order->branch_id, 404);
}

كل سطر بيعمل إيه؟

  • private: الدالة للاستخدام الداخلي في نفس class. authorizeBranch اسم اختاره المطوّر، مش Laravel magic method.
  • Request $request, Order $order: محتاجين هوية المستخدم والطلب اللي عايز يوصل له. void يعني مفيش قيمة مقصودة ترجع؛ إما تكمل أو توقف الطلب.
  • $request->user(): هات المستخدم الموثّق بالفعل. المسار محمي بـ auth وrole قبل استدعاء الـ controller.
  • abort_unless: امنع الوصول إلا لو واحد من الشرطين صحيح.
  • $user->isAdmin(): المدير يقدر يصل لأي فرع حسب قرار المشروع الحالي.
  • ||: أو؛ يكفي شرط واحد. بخلاف && اللي تحتاج كل الشروط.
  • (int): حوّل معرف الفرع لرقم قبل المقارنة الصارمة === لتجنب اختلاف تمثيل الرقم.
  • 404: المشروع اختار إخفاء وجود الطلب غير المسموح، مش معناه إن الطلب مش موجود فعلًا.
  • } يقفل الدالة. الدالة لا تعدّل بيانات.

القائمة كمان بتتفلتر في index على فرع الموظف. فلترة القائمة وحدها مش كفاية: المستخدم ممكن يطلب /api/staff/orders/123 مباشرة، ولذلك فيه فحص على مستوى الطلب المفرد.

نفّذ بإيدك: افترض staff فرعه 2، وطلب فرعه 3؛ قيّم الشرط. بعدين غيّر دور المستخدم إلى admin وقيّمه تاني. ما تعدّلش بيانات موظفين حقيقيين للتجربة.

المتوقع: staff يتوقف بـ404؛ admin يكمل. تأكد في المصدر إن show وupdateStatus بينادوا الدالة.

غلطة شائعة: تفترض إن route model binding أو وجود id في قاعدة البيانات يدي المستخدم صلاحية الوصول. التحميل غير التصريح.

سؤال إنترفيو: يعني إيه IDOR، وإيه علاقته بالمثال؟

وصول غير مسموح لعنصر بتغيير معرفه في URL أو الطلب. الحماية لازم تتحقق من صلاحية المستخدم على العنصر نفسه، مش مجرد إنه مسجل دخول أو إن الـ ID موجود.

08 — أسئلة وأمثلة: من السلة إلى الدفع

الدروس دي أهم من حفظ أسماء Stripe: افهم البيانات بتتحول إزاي، ومين صاحب قرار السعر، وإمتى نعتبر الدفع مؤكدًا. ذاكر سؤال واحد كل مرة، ومتجربش طلبات دفع أو مفاتيح production. لو عايز تجربة تكامل فعلية استخدم بيئة test مفصولة، مش حساب دفع حقيقي.

واقع المشروع: Cart.jsx فيها React وStripe Elements؛ csrfFetch تحول الطلبات إلى محاكاة لو VITE_DEMO_MODE مفعّل. وضع الديمو لا يجمع فلوس ولا يثبت عمل Laravel/Stripe. الكلام التالي يفرّق بين مسار Laravel الحقيقي وبين أي مثال مختصر.

1. أبعت السعر ولا أبعت معرف المنتج والكمية؟

مقتطف فعلي من Cart.jsx. داخل component عندها state للعميل والسلة والفرع؛ المقطع مش مستقل، ولا فيه إرسال بمجرد تعريفه.

const buildPayload = () => ({
    branch_id: Number(selectedBranchId),
    order_type: orderType,
    customer_name: customer.name,
    customer_phone: customer.phone,
    delivery_address: orderType === 'delivery' ? [deliveryArea, deliveryAddress].filter(Boolean).join(', ') : null,
    pickup_time: orderType === 'pickup' ? customer.pickupTime : null,
    payment_method: paymentMethod,
    items: cartItems.map((item) => ({ menu_item_id: item.id, quantity: item.quantity, notes: item.notes || null })),
});

كل سطر بيعمل إيه؟

  • const buildPayload = () => ({: دالة من غير arguments ترجع object مباشرة. الأقواس ({ ... }) تميز object الناتج عن جسم الدالة؛ مش body محتاج return.
  • branch_id: Number(...): المفتاح المتوقع من Laravel، وقيمته تحويل معرف الفرع إلى رقم.
  • order_type: نوع الاستلام من state. customer_name وcustomer_phone: انقل قيم الحقول إلى أسماء السيرفر المتوقعة.
  • delivery_address: الـ ternary condition ? A : B يختار العنوان للتوصيل فقط، وإلا null. [deliveryArea, deliveryAddress] قائمة جزأين، filter(Boolean) يشيل القيم falsy، وjoin(', ') يضم الباقي بفاصلة ومسافة.
  • pickup_time: وقت الاستلام لو pickup، وإلا null؛ مش كل الحقول مطلوبة لكل نوع طلب.
  • payment_method: كاش أو كارت حسب اختيار المستخدم؛ السيرفر ما زال يتحقق منها.
  • items: cartItems.map(...): حوّل كل عنصر إلى object جديد فيه المعرف والكمية والملاحظات فقط. || null يحول الملاحظة الفاضية إلى null هنا.
  • });: يقفل object والتعبير وينهي تعريف الدالة.

لاحظ إن العميل لا يرسل total ولا price هنا. إجمالي React للعرض، بينما السعر الموثوق من قاعدة البيانات. الدالة تبني بيانات فقط؛ طلب HTTP بيحصل لاحقًا لما نستخدم ناتج buildPayload() مع csrfFetch وJSON.stringify.

نفّذ بإيدك: اكتب عنصر سلة افتراضي فيه id/name/price/quantity، وتتبع ناتج map. استخدم بيانات وهمية، مش رقم أو عنوان شخص حقيقي.

المتوقع: الاسم والسعر يختفوا من payload الخاص بالبند؛ يبقى menu_item_id وquantity وnotes.

غلطة شائعة: تستخدم forEach بدل map وتتوقع array جديدة؛ أو تفترض إن إخفاء السعر من payload يغني عن حساب السيرفر.

سؤال إنترفيو: ليه `map` مناسبة هنا؟

لأننا محتاجين array جديدة ناتجة عن تحويل كل عنصر إلى الشكل اللي API تتوقعه. forEach تنفذ callback لكل عنصر لكن لا ترجع array نتائج.

2. السعر اتغيّر في المتصفح؛ مين يمنع دفع جنيه بدل190؟

مقتطف فعلي من OrderCreator.php. داخل foreach، بعد التحقق من المنتج وتوفره وقراءة pivot الخاص بالفرع. $order اتعملت داخل transaction، و$total بدأ بصفر.

$quantity = (int) $line['quantity'];

$order->items()->create([
    'menu_item_id' => $line['menu_item_id'],

  • $quantity = (int) $line['quantity']: اقرأ الكمية من بند الطلب المتحقق منه وحولها لعدد صحيح. التحويل نفسه مش بديل قواعد min/max.

سؤال إنترفيو: العميل عدّل localStorage للسعر؛ هل validation نوع الرقم كفاية؟

لأ. الرقم ممكن يكون صالحًا شكليًا لكنه سعر غلط. السيرفر يجيب السعر والتوفر من مصدره الموثوق ويحسب الإجمالي؛ السعر النهائي قرار business مش مجرد type validation.

3. إيه اللي بيتبعت إلى Stripe، وإيه اللي ماينفعش يظهر في React؟

مقتطف فعلي من StripePaymentGateway.php، داخل createIntent. الـ parameters معرفة في signature، وStripeClient مستوردة فوق.

$intent = (new StripeClient(config('services.stripe.secret')))->paymentIntents->create([
    'amount' => $amount,
    'currency' => $currency,
    'automatic_payment_methods' => ['enabled' => true],
    'metadata' => $metadata,
], ['idempotency_key' => $idempotencyKey]);

return ['id' => $intent->id, 'client_secret' => $intent->client_secret];

كل سطر بيعمل إيه؟

  • $intent: متغير نتيجة إنشاء محاولة الدفع. new StripeClient(...) يبني عميل مكتبة Stripe بمفتاح السيرفر الخاص المقروء من config، مش قيمة نحطها حرفيًا في الدرس.
  • ->paymentIntents->create([: اطلب إنشاء PaymentIntent بإعدادات المبلغ والدفع.
  • 'amount' => $amount: المبلغ بوحدات العملة الصغرى حسب العملة. الـ controller عندنا يحول جنيهات EGP إلى قروش بالضرب في100 ثم التقريب والتحويل لعدد صحيح قبل الإرسال.
  • 'currency' => $currency: العملة؛ controller المشروع يمرر egp.
  • automatic_payment_methods: إعداد يفعّل طرق الدفع التلقائية المتاحة بحسب Stripe؛ مش ضمان إن كل وسيلة متاحة لكل حساب أو بلد.
  • metadata: بيانات ربط مثل order_id؛ مش بيانات بطاقة ولا مكان مناسب لمعلومات حساسة غير لازمة.
  • ['idempotency_key' => ...]: خيارات الطلب إلى Stripe لمنع تكرار إنشاء نفس العملية عند إعادة المحاولة بنفس المفتاح المناسب.
  • آخر return: رجّع id وclient_secret للـ controller، اللي يرجع بيانات لازمة للواجهة. القوس [] هنا PHP array.

client_secret يسمح للعميل بمتابعة Intent المحدد؛ مش هو مفتاح الحساب الخاص ولا حاجة ننشرها في logs. VITE_STRIPE_KEY في React لازم يكون publishable key فقط، لأن قيم VITE بتظهر في كود المتصفح. CardElement وconfirmCardPayment يرسلان بيانات البطاقة إلى Stripe؛ Laravel عندنا لا يحتاج رقم البطاقة الخام.

نفّذ بإيدك: حدد على الورق أماكن publishable key وsecret key وclient_secret. ما تفتحش أسرار حسابك ولا تنسخها للتوثيق.

المتوقع: publishable key للواجهة، secret key للسيرفر، وclient_secret لعملية دفع محددة وللعميل المعني فقط.

غلطة شائعة: تعمل VITE_STRIPE_SECRET وتفتكر تغيير اسم المتغير يخفي قيمته؛ أو تعتبر إنشاء PaymentIntent معناه إن الفلوس اتحصلت.

سؤال إنترفيو: ليه إنشاء عملية الدفع يتم من backend؟

لأن فيه سر حساب ومبلغ لازم يكون موثوقًا ومحسوبًا على السيرفر. المتصفح يتعامل مع خطوة التأكيد الآمنة، مش تحديد المبلغ النهائي أو امتلاك المفتاح الخاص.

4. لو نفس طلب الدفع اتبعت مرتين، إزاي نمنع التكرار؟

مثال مبسّط من Cart.jsx. داخل async payment handler، وpayload دالة تمرر بيانات الطلب. الأصل يحيط العملية بـ try/catch/finally ويمنع ضغطات متزامنة في الواجهة.

const idempotencyKey = crypto.randomUUID();
const response = await csrfFetch('/api/payments/intents', {
    method: 'POST',
    headers: { 'Idempotency-Key': idempotencyKey },
    body: JSON.stringify({
        ...payload(),
        payment_method: 'card',
        idempotency_key: idempotencyKey,
    }),
});

كل سطر بيعمل إيه؟

  • crypto.randomUUID(): اعمل معرفًا عشوائيًا للمحاولة. مش كلمة سر، لكنه لازم يمثل العملية المقصودة بوضوح.
  • await csrfFetch(...): اطلب من Laravel بدء الدفع واستنى الرد. في demo mode ده محاكاة حسب الـ helper، مش طلب Stripe حقيقي.
  • method: 'POST': إنشاء عملية، مش قراءة فقط.
  • headers: { ... }: ابعت المفتاح في HTTP header بالاسم المتفق عليه.
  • body: JSON.stringify({: ابنِ object ثم حوّله إلى JSON.
  • ...payload(): انسخ خصائص بيانات الطلب إلى object جديد؛ ده spread syntax.
  • payment_method: 'card': تأكيد طريقة الدفع. وجوده بعد spread يخليه يغلب قيمة بنفس الاسم جاية من payload.
  • idempotency_key: نفس المفتاح في body كمان؛ السيرفر يفضّل header ثم fallback للـ body.
  • }), يقفل object وstringify، و}); يقفل خيارات الطلب والاستدعاء.

في PaymentController، لو المفتاح موجود بالفعل يرد409 مع order_id ورسالة، مش يرجّع client_secret لنفس المحاولة. كمان قاعدة البيانات عليها unique constraint؛ الفحص الأول وحده لا يمنع طلبين متزامنين من العبور قبل الحفظ.

نفّذ بإيدك: افترض محاولة K1 ثم retry بنفس K1، وبعدها محاولة K2. حدّد أيهم السيرفر يقدر يتعرف عليه كتكرار. ده تمرين تتبع؛ لا تبعت دفعات حقيقية.

المتوقع: إعادة K1 مرتبطة بالمحاولة السابقة؛ K2 عملية مختلفة من وجهة نظر المفتاح.

غلطة شائعة في الكود الحالي: UUID تتولّد داخل كل استدعاء pay. ضغط لاحق بعد خطأ شبكة يعمل مفتاحًا جديدًا؛ بالتالي ده مش نظام retries كامل. التطوير الأفضل يحافظ على مفتاح المحاولة نفسها عند retry ويصمم رد إعادة الاستخدام آمنًا. تعطيل الزر وحده لا يحمي السيرفر.

سؤال إنترفيو: يعني إيه idempotency؟

إعادة نفس العملية المقصودة لا تضاعف أثرها. في الدفع محتاج هوية للمحاولة، قيود تخزين ومعالجة تزامن مناسبة، وسياسة واضحة لرد retry؛ مجرد UUID جديد كل مرة مش كفاية.

5. صفحة النجاح قالت تم الدفع؛ ليه لسه محتاج webhook؟

مقتطف فعلي من PaymentController.php، بداية method webhook؛ $gateway تنفيذ PaymentGateway المجهز من Laravel.

try {
    $event = $gateway->parseWebhook($request->getContent(), (string) $request->header('Stripe-Signature'));
} catch (Throwable) {
    return response()->json(['message' => 'Invalid webhook signature.'], 400);

كل سطر بيعمل إيه؟

  • try {: حاول تنفيذ كود ممكن يفشل، ووجّه الفشل إلى catch بدل متابعة الدفع كأنه صحيح.
  • $request->getContent(): جسم الطلب الخام كما وصل؛ التحقق من التوقيع محتاجه، مش JSON فكّيته وركّبته تاني بشكل مختلف.
  • $request->header('Stripe-Signature'): التوقيع المرسل. (string) يحول النتيجة إلى نص.
  • $gateway->parseWebhook(...): التنفيذ الحقيقي في StripePaymentGateway.php يستخدم Webhook::constructEvent مع webhook secret؛ مش مجرد JSON.parse يثق في الرسالة.
  • $event = ...: خزّن الحدث بعد نجاح التحقق.
  • catch (Throwable): لو حصل exception، ادخل هنا. النوع ده يغطي أخطاء PHP وexceptions؛ المشروع يعامل فشل هذه الخطوة كرسالة غير صالحة.
  • return response()->json(..., 400): رد خطأ وأوقف المسار؛ ما تحدثش الطلب. } يقفل catch.

بعد التحقق، الكود يطابق gateway_reference مع Intent ويعالج payment_intent.succeeded: يغير payment_status إلى paid والحالة إلى new ويسجل التحول داخل transaction. البداية كانت payment_pending، وقائمة الموظفين تخفي طلبات الكارت غير المدفوعة. عدم وجود order مطابق يرجع received=true من غير تعديل.

نفّذ بإيدك: اقرأ اختبار test_verified_payment_webhook_marks_order_paid_once في OrderOperationsTest.php. حدّد عدد إرسال الحدث وعدد سجلات التاريخ المتوقع. لا تبعت webhook يدوي للإنتاج.

المتوقع: الاختبار يرسل مرتين متتاليتين ويتوقع سجلًا واحدًا. بيستخدم gateway fake؛ لذلك لا يثبت إن التحقق الحقيقي من توقيع Stripe اتجرب.

غلطة شائعة: تعتبر إشعار المتصفح إثبات الدفع، أو تقول إن الكود محصّن تمامًا من التزامن. شرط payment_status !== 'paid' الحالي قبل transaction يمنع التكرار المتتابع المعتاد، لكن حدثين متزامنين ممكن يعدّوا الشرط معًا. تحسينه يحتاج row locking وإعادة فحص أو معالجة event IDs/unique transitions وتصميم إعادة المحاولة. والملف لا يمثل دورة refunds كاملة.

2. سؤال: ليه لازم ننضّف مؤقت التحديث؟

مقتطف فعلي داخل StaffDashboard:

  1. useEffect يشغّل side effect بعد ظهور المكوّن؛ () => {} الدالة اللي React هيناديها.

هو polling؛ التغيير ممكن يتأخر لحد التحديث التالي. WebSocket أو SSE طرق أخرى لدفع التحديث من السيرفر، لكن متدّعيش إن الواجهة الحالية تستخدمهم. المؤقت هو اللي بيرسل الطلبات هنا.

السطر الأول يأخذ الطلبات أو قائمة فاضية. fresh مجرد اسم «النسخة الجديدة من الرد»، مش معنى إن كل عناصرها وصلت حالًا.

السطر الثاني لا ينادي notify في أول تحميل؛ loadedOnce.current تبدأ بـ false. بعد أول تحميل نستخدم filter لاختيار الطلبات اللي حالتها new وID بتاعها مش موجود في المجموعة القديمة. && يشترط الاتنين. has تختبر وجود المعرّف، و! يعكس النتيجة. notify يعرض رسالة ويحدد IDs للتظليل؛ الصوت يتطلب تفعيل المستخدم بسبب قيود المتصفح.

السطر الثالث يعمل map لاستخراج IDs، ثم new Set يبني مجموعة بدون تكرارات. نخزنها في ref علشان المقارنة في الرد القادم. الرابع يسجل اكتمال أول تحميل. الخامس يحدّث React state بالطلبات؛ ده اللي يعيد رسم الكروت، على عكس تحديث refs.

تطبيق يدوي — مثال تدريبي إضافي في Console:

const known = new Set([10, 11]);
const fresh = [{ id: 11 }, { id: 12 }];
console.log(fresh.filter((order) => !known.has(order.id)));

الأول IDs معروفة، الثاني الرد الجديد، الثالث يستبعد المعروفة. المتوقع: array فيها { id: 12 } فقط. في المشروع فيه شرط الحالة كمان، وتتصفّر ذاكرة المقارنة عند تغيير الفرع أو التاريخ.

غلطة شائعة: تحديث knownIds قبل المقارنة؛ كده كل IDs الرد بقت معروفة ومش هتكتشف جديد.

سؤال إنترفيو: useRef ولا useState؟

استخدم state لبيانات لازم تغييرها يظهر على الشاشة، وref لقيمة تستمر بين renders من غير ما تغييرها يسبب render، زي IDs المعروفة أو معرّف مؤقت. الـ ref مش بديل أسرع تلقائيًا لكل state.

4. سؤال: إزاي أغيّر حالة الطلب وأمنع تضارب موظفين؟

مقتطف فعلي من updateStatus، داخل try:

const response = await csrfFetch(`/api/staff/orders/${order.id}/status`, {
    method: 'PATCH',
    body: JSON.stringify({ status, reason, expected_status: order.status }),
});
setOrders((current) => current.map((item) => item.id === order.id ? response.order : item));
setMessage(response.message);
setReasonAction(null);
  1. نرسل طلبًا ونستنى الرد. backticks تعمل template literal؛ ${order.id} تضع ID في URL. order وstatus وreason مدخلات الدالة الأصلية.
  2. PATCH معناها تحديث جزئي لمورد.
  3. JSON.stringify يحوّل البيانات لنص JSON. { status, reason } اختصار { status: status, reason: reason }. expected_status هي الحالة اللي الموظف شافها قبل الضغط.
  4. إغلاق options واستدعاء الطلب.
  5. functional setter يستقبل أحدث قائمة current. map تستبدل الطلب المطابق بالنسخة اللي رجعها السيرفر؛ الباقي كما هو. مش بنفترض إن تغيير اللون محليًا معناه نجاح السيرفر.
  6. عرض رسالة الرد.
  7. إغلاق اختيار سبب الإلغاء/الرفض باستخدام null.

ليه expected_status؟ لو موظف تاني نقل الطلب بعد ما شفته، السيرفر الحقيقي يقارن الحالة داخل transaction مع قفل الصف. لو اختلفت يرجع 409، والواجهة تعيد جلب الطلبات. الـ backend كمان يفحص الانتقالات المسموحة وسبب الإلغاء؛ مش أي status في الواجهة تبقى مقبولة.

تطبيق: بحسابات تجريبية وطلبات وهمية فقط، جرّب نقل طلب preparing إلى ready. المتوقع الكارت ينتقل لعمود Ready بعد النجاح. لو بتختبر ديمو Cloudflare، دي محاكاة محلية وليست دليلًا على اختبار قفل قاعدة البيانات.

غلطة شائعة: تغيير الحالة محليًا وإهمال response أو catch؛ الموظف يظن الطلب اتقبل بينما السيرفر رفضه. الكود الحالي يعرض الخطأ ويمسح busy state في finally.

سؤال إنترفيو: UI تمنع الضغط مرتين، هل كده منعنا كل race conditions؟

لأ، فيه تبويبات وأجهزة وموظفين غيرك. منع التكرار في الواجهة يحسن التجربة، لكن backend لازم يتحقق من الحالة والصلاحية ويستخدم transaction/locking حسب العملية. في المشروع expected_status يكشف إن البطاقة قديمة.

حدود لازم تعرفها: today() الحالية تستخدم toISOString()، يعني UTC وقد تختلف عن اليوم المحلي قرب منتصف الليل. مؤقت تظليل الطلب داخل notify ليس له cleanup مستقل حاليًا؛ تنظيف polling لا ينظف كل timeout تلقائيًا. دي نقاط تحسين، مش مزايا مكتملة.

2. زوّدت quantity: ليه map مش تعديل مباشر؟

المصدر: Cart.jsx.

مقتطف فعلي:

const updateItem = (id, changes) => {
    const next = cartItems.map((item) => item.id === id ? { ...item, ...changes } : item);
    setCartItems(next);
    writeCart(next);
};
  • (id, changes) مدخلان: مين يتعدل؟ وإيه الخصائص الجديدة؟
  • map يمر على السلة ويرجع array جديدة.
  • item.id === id يحدد العنصر المقصود.
  • condition ? A : B يرجع object جديد للمطابق والعنصر القديم للباقي.
  • { ...item, ...changes } ينسخ البيانات؛ خصائص changes اللاحقة تكسب لو نفس الاسم.
  • setCartItems(next) يحدّث React state والعرض.
  • writeCart(next) يكتب localStorage ويطلق event لتحديث عداد السلة في نفس التبويب.

تمرين جديد مبسّط، داخل Cart حيث الدالة موجودة:

updateItem(1, { quantity: 3 });

المتوقع: العنصر id=1 فقط يتحدث لو موجود. ما تشغّلش النداء مباشرة في body المكوّن كل render؛ جرّبه من handler زر.

خطأ شائع: localStorage وحدها بتخلي React يرندر؟ لأ؛ setter أو listener يزامن state. حدث storage العادي لا ينطلق في نفس التبويب اللي عمل الكتابة، لذلك فيه custom event.

إنترفيو: هل سعر السلة موثوق للدفع؟ لا؛ preview من الفرونت. Laravel يحسب السعر من DB.

بإيدك: قارن بـ Number(selectedServiceId) بعد التأكد إن المدخل صالح؛ المتوقع object السعر 300. في Vue select المثال الصحيح :value="service.id" يمرّر الرقم أصلًا.

غلطة شائعة: تغيّر === إلى == بدون فهم أصل اختلاف البيانات.

JavaScript: افهم الناتج قبل تشغيل الكود

المصدر المرجعي: Cart، CatalogContext. تطبيق أوسع في 12.

1. إمتى تستخدم find وإمتى filter؟

const services = [{ id: 1, price: 50 }, { id: 2, price: 30 }];
const selected = services.find((service) => service.id === 2);
const cheap = services.filter((service) => service.price < 40);
الإجابة

find ترجع أول object مطابق أو undefined، filter ترجع array جديدة حتى لو فاضية. هنا selected object الخدمة 2، وcheap array فيها الخدمة 2. service عنصر callback الحالي، و=== مقارنة صارمة.

2. ليه الشرط ده false؟

const selectedId = '2';
const matches = 2 === selectedId;
الإجابة

الأنواع مختلفة: رقم ونص. ظبط النوع عند حدود الإدخال حسب البيانات؛ في Vue :value="service.id" تحفظ الرقم، وفي بعض HTML inputs القيمة نص. ما تستبدلش كل === بـ == لمجرد إخفاء المشكلة.

3. إيه الناتج؟ وليه spread هنا؟

const item = { id: 1, quantity: 1 };
const next = { ...item, quantity: 3 };
console.log(item.quantity, next.quantity);
الإجابة

1 3؛ عملنا object جديد وغيّرنا خاصية فيه. spread shallow، فـ nested object يفضل مرجع مشترك لو ما نسخناهوش. ده أساس immutable updates في React.

4. إجمالي السلة يتحسب إزاي؟

const items = [{ price: 50, quantity: 2 }, { price: 30, quantity: 1 }];
const total = items.reduce((sum, item) => sum + item.price * item.quantity, 0);
الإجابة
  1. 0 بداية accumulator؛ كل مرة نضيف سعر السطر × الكمية. ده preview في الفرونت؛ Laravel يعيد الحساب بأسعاره. استخدام numbers مالية floating-point له حدود؛ في تصميم إنتاج قوي فكّر في minor units/decimal strategy واضحة.

5. إيه الفرق بين ?? و||؟

const fee = 0;
console.log(fee ?? 20);
console.log(fee || 20);
الإجابة

الأول 0، التاني 20. ?? يستخدم البديل مع null/undefined فقط؛ || مع أي falsy. ده مهم في مجاني/صفر، مش فرق شكلي.

6. await بيجمّد الصفحة؟ وfetch بترمي error على 422؟

const response = await fetch('/api/menu');
if (!response.ok) throw new Error('Request failed');
const data = await response.json();
الإجابة

الكود ده داخل async function. await يوقف تكملة الدالة مؤقتًا، مش event loop كلها. fetch لا ترفض لمجرد HTTP 422؛ افحص ok/status. network failure ممكن يرفض Promise. json قراءة body async، مش نفس stringify.

تمرين المجموعة: اكتب function ترجع أسماء الخدمات الأرخص من 40 بـ filter ثم map. المتوقع: قائمة أسماء، مش object واحد. خطأ شائع: forEach لا ترجع array نتائج.

المصدر: AutoCare App، useGarage. التدريب المفصل في 13.

7. ref وcomputed: كل واحدة إمتى؟

const selectedId = ref('');
const selected = computed(() => services.find((service) => service.id === selectedId.value));
الإجابة

ref لحالة الاختيار القابلة للتغيير؛ computed لنتيجة مشتقة تتحدث عند تغير reactive dependencies. services لازم تكون معرّفة. في JavaScript نقرأ .value؛ في template Vue يفك ref تلقائيًا في الاستخدام ده. ما أخزنش selected كنسخة state مستقلة وأتعب في مزامنتها بدون داعي.

8. ليه :value و:key مختلفين رغم نفس الرقم؟

<option v-for="service in services" :key="service.id" :value="service.id">
    {{ service.name }}
</option>
الإجابة

key لهوية عنصر القائمة بالنسبة لـ Vue عند التحديث. value قيمة اختيار المستخدم. : تربط JavaScript expression؛ من غيرها value="service.id" نص حرفي. service متاح في نطاق v-for، مش كل المكوّن.

9. v-model بتعمل إيه؟

الإجابة

مزامنة بين قيمة الإدخال وstate باستخدام الربط وأحداث التحديث المناسبة. اختيار select يغير selectedId، وتغيير selectedId برمجيًا يعكس الاختيار. مش بتبعت البيانات للسيرفر تلقائيًا.

الإجابة

v-if ينشئ/يزيل الفرع ومكوّناته، وv-show يبدّل display ويُبقي العنصر. اختيارهم حسب تكرار التبديل والتكلفة. opacity:0 شيء مختلف: العنصر قد يظل قابلًا للتركيز/التفاعل لو ما اتعالجش.

onMounted(() => window.addEventListener('scroll', updateNavbar));
onBeforeUnmount(() => window.removeEventListener('scroll', updateNavbar));
الإجابة

لمنع بقاء listener بعد إزالة المكوّن أو تكرار التسجيل. نزيل نفس function reference ونفس event، مش arrow function جديدة تبدو متشابهة. updateNavbar بدون أقواس لأننا بنمرر الدالة للتنفيذ لاحقًا.

تمرين المجموعة: اختار خدمة واعرض السعر، ثم غيّر الاختيار. المتوقع: السعر يتحدث من computed بدون change handler إضافية. خطأ شائع: استخدام اسم service خارج نطاق v-for بدل selectedService.

المكتبات: أسئلة «ليه دي موجودة؟» بدل حفظ الأسماء

1. Vite بيشغّل Laravel؟

لأ. Vite مسؤول عن frontend development/build؛ PHP يشغّل Laravel. مثالهم متكامل، لكن مش نفس العملية.

المصدر: Pizza vite.config.js. مقتطف فعلي من plugins:

plugins: [
    laravel({
        input: ['resources/css/app.css', 'resources/js/app.jsx'],
        refresh: true,
    }),
    react(),
],
  • plugins قائمة إضافات Vite.
  • laravel(...) يربط entry points وتكامل Blade/dev server/manifest.
  • input الملفات اللي يبدأ منها تتبع imports والبناء.
  • refresh: true يساعد في full reload عند تغيّر ملفات Laravel المتابعة؛ مش نفس React component refresh وحده.
  • react() plugin معالجة React وتحسين تجربة التطوير.
  • في AutoCare الإضافة المقابلة vue()؛ Portfolio يستخدم React plugin من غير Laravel plugin.

تمرين: افتح AutoCare vite.config.js وحدد entry file. المتوقع: resources/js/app.js، مش app.jsx.

خطأ شائع: فتح port Vite وتوقّع API Laravel تشتغل منه تلقائيًا. ادخل عنوان Laravel للنسخة المحلية، وخلي Vite يقدّم assets.

إنترفيو: ليه المتصفح ما بيحمّلش .vue خام؟ لأن Vue plugin يحوّلها إلى JavaScript قابل للتنفيذ. TypeScript/JSX كذلك يحتاجان معالجة مناسبة.

2. dependencies وdevDependencies يعني إيه فعلًا؟

مثال مبسّط، مش نقل تصنيف المشروع حرفيًا:

{
    "dependencies": { "vue": "^3.0.0" },
    "devDependencies": { "vite": "^7.0.0" }
}
  • dependencies حزم تعتمد عليها الشيفرة أو التطبيق؛ devDependencies أدوات مطلوبة للتطوير/البناء/الاختبار.
  • ^ range توافق، مش الإصدار المثبت الدقيق. الأرقام هنا توضيحية فقط؛ راجع manifests الحقيقية.
  • JSON يحتاج مفاتيح ونصوص بين double quotes، ومفيش trailing comma في JSON القياسي.
  • التصنيف لا يقرر وحده ما يدخل bundle: imports وbuild configuration هما الأساس.
  • ممكن حزمة frontend موجودة في devDependencies تدخل bundle لو استوردتها؛ العكس أداة build مصنّفة dependencies لا يجعلها واجهة للمستخدم.

في manifests الحالية plugin Vue وplugin React بتاع Pizza مكتوبين تحت dependencies، رغم إن دورهما build tooling. ده مش معناه إن المستخدم يشغّل plugin داخل المتصفح.

تمرين: افتح Pizza package.json وابحث عن axios. هل وجودها يكفي لإثبات استخدامها؟ المتوقع: لا؛ راجع imports ومسار التنفيذ.

خطأ شائع: تثبيت dependencies بدون devDependencies قبل frontend build ممكن يفقد Vite؛ غالبًا أدوات البناء مطلوبة في مرحلة build ثم تُسلّم artifacts.

إنترفيو: ما الفرق بين install وupdate؟ install يعتمد على lock لإعادة نفس الشجرة عند وجوده؛ update يعيد حل إصدارات ضمن الحدود ويغيّر lock. ما تعملش update شامل من غير اختبار.

3. لو fetch موجودة، ليه Axios؟ وليه csrfFetch؟

مقتطف فعلي من Pizza API helper:

const response = await fetch(url, {
    credentials: 'same-origin',
    ...options,
    headers,
});
  • fetch API أصلية في المتصفح، مش package في npm.
  • credentials إرسال بيانات اعتماد مثل cookies للـ same-origin.
  • ...options يمرّر method/body وخيارات المستدعي؛ الترتيب يسمح باستبدال قيمة سابقة.
  • headers قيمة object تم تجهيزها فوق المقتطف، فيها قبول JSON وCSRF عند توفره.
  • helper يكمل تحليل JSON ويرمي error مع فشل HTTP، ويحوّل الطلبات لـ demoFetch في demo mode.

الحقيقة الحالية:

  • Pizza ثبت Axios لكن الكود النشط للطلبات يستخدم csrfFetch المبني على fetch؛ bootstrap.js بتاعه مش ملف Axios starter.
  • AutoCare bootstrap.js فعلًا يستورد Axios ويضع window.axios؛ لكن بيانات الجراج الحالية محفوظة محليًا، وده مش API booking حقيقية.
  • ما تفترضش إن ملف اسمه bootstrap.js يعني مكتبة Bootstrap؛ الاسم مجرد startup module. Pizza يستورد Bootstrap CSS بشكل منفصل.

تمرين: قارن Pizza bootstrap وAutoCare bootstrap. المتوقع: نفس اسم الملف، مسؤوليتان مختلفتان حسب محتواه.

خطأ شائع: استخدام fetch وAxios بالتبادل في كل مكان بدون توحيد handling للجلسة والأخطاء.

إنترفيو: ليه helper؟ لتوحيد السلوك المشترك، مش لإخفاء فهم HTTP أو الاستغناء عن backend security.

4. Stripe browser وStripe PHP: ليه حزمتين؟

مصادر: Cart، StripePaymentGateway.

مقتطف فعلي من داخل الدفع في Cart:

const result = await stripe.confirmCardPayment(response.client_secret, {
    payment_method: { card: elements.getElement(CardElement) },
});
  • stripe أداة المتصفح من Stripe.js، وReact bindings توفر hooks/components.
  • client_secret خاص بـ PaymentIntent ضمن التدفق المقصود؛ مش server secret API key، وبرضه ما تنشروش عشوائيًا.
  • CardElement إدخال Stripe؛ raw card details لا تتحول لحقول Laravel عندنا.
  • PHP package تنشئ intent وتتحقق من webhook على السيرفر. جواب المتصفح مش بديل للتأكيد المتحقق منه.

تمرين سؤال فقط: Stripe secret key ينفع في متغير VITE_؟ المتوقع: لا؛ هيظهر في شيفرة العميل.

خطأ شائع: وجود Stripe packages يعني الدفع live جاهز ومختبر؟ لا. الديمو يحاكي التدفق ولا يستقبل دفع حقيقي.

إنترفيو: الفصل client/server يقلّل تعرض بيانات البطاقة ويحافظ على أسرار إنشاء الدفع في السيرفر؛ لا يلغي التزامات وإعدادات التشغيل الآمن.

أسئلة تطوير إضافية: أطبّق اللي اتعلّمته إزاي؟

الفهرس · ده بنك تمارين، مش قائمة عيوب مؤكدة في النسخة الحالية.

التقرير القديم كان مؤرخًا 9 أكتوبر ووصف كودًا اتغيّر بعده. مثلًا MenuPage الآن تستخدم CatalogContext، وفيه Admin وtracking حاليًا؛ متتعاملش مع الاقتراحات القديمة كأنها كلها ناقصة. النسخة الأصلية محفوظة في الأرشيف.

سؤال 1: أضيف بحث عن الخدمة بالاسم؟

في مكوّن Vue تدريبي يحتوي services، استورد ref وcomputed ثم أضف:

const search = ref('');
const filteredServices = computed(() => {
    const query = search.value.trim().toLowerCase();
    return services.filter((service) => service.name.toLowerCase().includes(query));
});
  1. نص البحث reactive وفاضي في البداية.
  2. النتيجة مشتقة من نص البحث وقائمة الخدمات.
  3. trim تشيل الفراغات الطرفية؛ toLowerCase توحّد حالة الحروف، بدون تعديل services الأصلية.
  4. filter ترجع قائمة المطابقات؛ includes تبحث عن النص داخل الاسم؛ كل اسم بنحوّله lowercase علشان الطرفين متوافقين.
  5. نهاية الحساب.

بإيدك: أضف <input v-model="search" aria-label="Search services">، وخلّي v-for تلف على filteredServices بدل services. كلمة oil تعرض Oil Change. نص مفيش له نتيجة يعرض قائمة فاضية؛ اعمل رسالة مناسبة.

غلطة شائعة: فلترة القائمة الأصلية وإعادة استبدالها في كل حرف؛ تفقد باقي البيانات بدل اشتقاق نتيجة منها.

سؤال إنترفيو: البحث ده يكفي لكتالوج ضخم؟

الإجابةلأ بالضرورة؛ مع بيانات كبيرة نحتاج server filtering وpagination وربما debounce ونتعامل مع ترتيب وصول النتائج.

سؤال 2: أضيف loading وأمنع الضغط المتكرر على زر؟

في مكوّن Vue تدريبي استورد ref؛ الدالة هنا محاكاة انتظار فقط، لا تنشئ طلبًا حقيقيًا:

const saving = ref(false);
async function savePractice() {
    if (saving.value) return;
    saving.value = true;
    try {
        await new Promise((resolve) => setTimeout(resolve, 500));
    } finally {
        saving.value = false;
    }
}
  1. حالة التحميل.
  2. async دالة غير متزامنة.
  3. guard يمنع تنفيذ ثانٍ أثناء الانتظار.
  4. ابدأ حالة الانتظار. 5–6. محاكاة Promise تنتهي بعد 500ms؛ مش طلب شبكة. 7–9. finally ترجع الحالة حتى لو حصل خطأ؛ مفيش catch هنا لأن مثالنا مش بيضيف فشل متعمّد.
  5. نهاية الدالة.

بإيدك: اربط زر بـ @click="savePractice" و:disabled="saving" واعرض saving كنص. المتوقع الزر يقف نصف ثانية ثم يرجع.

غلطة شائعة: اعتبار تعطيل الزر حماية من تكرار الطلب في السيرفر؛ المستخدم يقدر يعيد الطلب من خارج الواجهة.

سؤال إنترفيو: الحل على السيرفر لتكرار طلب دفع؟

الإجابةتصميم idempotency وربط محاولة واحدة بهوية ثابتة وقيود مناسبة؛ الدرس الفعلي في [الدفع](08-checkout-and-payment.md).

سؤال 1: أحط محتوى الصورة في DB ولا مسارها؟

في المشروع ده بنخزّن مسار الصورة. مثال تدريبي إضافي:

  1. object لبيانات المنتج؛ مش سجل DB حقيقي بالـid ده.
  2. معرّف تدريبي؛ ما تربطوش بمنتج حقيقي لمجرد تشابه رقم id.
  3. الاسم المعروض.
  4. URL بالنسبة لأصل الموقع؛ يبدأ slash مش مسار Windows.
  5. نهاية object.
  6. اطبع المسار للتأكد من البيانات.

الملف الفعلي لهذا المسار يكون تحت public/images/menu/diavola.webp. المتصفح لا يكتب public في URL.

بإيدك: افتح /images/menu/diavola.webp من نفس أصل موقع Pizza المحلي. المتوقع الصورة لو الملف موجود ومتقدم من السيرفر.

غلطة شائعة: D:\... أو /public/images/... في src؛ ده مش URL الصورة في إعداد المشروع المعتاد.

سؤال إنترفيو: مسار الملف المحلي هو نفس URL؟

الإجابةلأ؛ السيرفر بيربط public root بمسارات URL؛ المتصفح يحتاج عنوانًا يقدر يطلبه.

سؤال 2: أعمل mapping للأسماء بدل التخمين؟

مثال تدريبي إضافي بنفس أسماء أصول التقرير القديم:

const photoMap = {
    Diavola: '/images/menu/diavola.webp',
    Carnivora: '/images/menu/carnivora.webp',
};
const photo = photoMap['Diavola'] ?? null;
console.log(photo);
  1. قاموس مفاتيحه أسماء والقيم مسارات. 2–3. كل منتج له مسار معروف، بدل اختيار صورة عشوائية.
  2. نهاية القاموس.
  3. [] قراءة خاصية بالاسم؛ ?? تستخدم null لو القيمة null أو undefined.
  4. يطبع مسار Diavola.

بإيدك: جرّب اسم Missing. المتوقع null؛ اعرض placeholder بدل تخمين صورة.

غلطة شائعة: اختلاف spelling أو case. في الأنظمة الفعلية يفضّل الربط بهوية منتج ثابتة أو حقل واضح في DB، مش الاسم المتغيّر فقط.

سؤال إنترفيو: ليه ?? مش بالضبط زي ||؟

الإجابة?? تستخدم البديل فقط مع null/undefined؛ || تستخدمه مع كل falsy مثل 0 أو نص فاضي كمان.

التالي: التعامل مع فشل الصورة والتحقق من الرفع.

أسئلة كود: صورة المنتج مش موجودة أو فشلت؟

الفهرس · موضوع الدرس React state + عرض شرطي + معالجة ملف في backend. مش مطلوب تذاكر تصميم الصور نفسه.

قائمة الصور الناقصة القديمة محفوظة في التقرير الأصلي. هي snapshot وقت التقرير، مش inventory حي لقاعدة بياناتك الآن. الصور الأصلية لم يتم تغييرها أثناء تعديل ملفات الدراسة.

سؤال 1: إزاي الواجهة تكتشف فشل الصورة؟

مثال مبسّط من MenuImage في MenuPage. اكتب مكوّن تدريب مستقل؛ استورد useState:

import { useState } from 'react';
function ProductImage({ item }) {
    const [failed, setFailed] = useState(false);
    if (!item.image_path || failed) return <p>Photo coming soon</p>;
    return <img src={item.image_path} alt={item.name} onError={() => setFailed(true)} />;
}
  1. استيراد حالة React.
  2. مكوّن يستقبل المنتج في props؛ { item } تفكيكها.
  3. حالة فشل تبدأ false ودالة تحديثها setFailed.
  4. ! ينفي وجود المسار؛ || يكفي أي شرط؛ لو مفيش صورة أو فشلت ارجع بديلًا.
  5. استخدم الصورة واسم المنتج كوصف؛ onError يحدّث الحالة لو التحميل فشل، فيعيد React العرض بالبديل.
  6. نهاية المكوّن.

بإيدك: اعرضه بمنتج صورة مساره /missing-photo.webp. المتوقع النص البديل، مش صورة مكسورة مستمرة. لو غيرت المنتج في نفس instance، حالة failed لا تتصفر تلقائيًا؛ استخدم key مستقرة مناسبة للمنتج أو صمّم reset مقصود.

غلطة شائعة: تعيد تعيين صورة معطوبة أخرى داخل onError بلا حد، فتعمل حلقة فشل.

سؤال إنترفيو: إيه الفرق بين alt وfallback؟

الإجابةalt وصف بديل للصورة، fallback قرار واجهة لعرض بديل عند غيابها أو فشلها؛ مش نفس الخاصية.

سؤال 2: الرفع من المتصفح كفاية لحماية السيرفر؟

مقتطف فعلي من AdminProductRequest، سطر داخل array قواعد validation:

'image' => ['nullable', 'image', 'mimes:jpeg,png,webp', 'max:8192'],
  • 'image' اسم حقل الطلب؛ => ربط المفتاح بقواعده.
  • nullable يسمح بعدم إرسال صورة.
  • image يتحقق من كون الملف صورة مدعومة.
  • mimes:... يقيد الأنواع المقبولة، مش اسم الملف المعروض فقط.
  • max:8192 حد الملف بالكيلوبايت في validation الملفات، مش أبعاد الصورة.
  • [] قائمة القواعد؛ الفاصلة نهاية عنصر داخل rules array، مش PHP script كامل مستقل.

بإيدك: اكتب اختبارًا يتوقع validation error لملف نصي بدل صورة، في بيئة الاختبار فقط. متحاولش ترفع ملفات مؤذية لتجربة الموقع العام.

غلطة شائعة: الاعتماد على accept داخل input؛ ده توجيه للمتصفح مش فحص أمان من السيرفر.

سؤال إنترفيو: هل validation تكفي وحدها؟

الإجابةلأ؛ نحتاج authorization وأسماء وتخزين آمنين وحدود موارد ومعالجة وفحص أخطاء مناسبين. القواعد دي جزء من الحماية.

سؤال 3: السيرفر بيصغّر الصورة مع الحفاظ على نسبتها إزاي؟

مقتطف فعلي من ProductImageService، داخل store بعد فك الصورة:

$width = imagesx($source);
$height = imagesy($source);
$targetWidth = min(800, $width);
$targetHeight = max(1, (int) round($height * ($targetWidth / $width)));
  1. عرض الصورة الأصلية بالبكسل؛ $source صورة اتقرأت بالفعل.
  2. ارتفاعها.
  3. العرض المستهدف أصغر القيمتين؛ الصورة الصغيرة مش بيكبّرها لـ800.
  4. نفس نسبة التصغير للارتفاع؛ round تقريب؛ (int) عدد صحيح؛ max يمنع ارتفاع أقل من1.

بإيدك: احسب لصورة 1600×1000. المتوقع 800×500. ولصورة 400×300 تفضل 400×300.

غلطة شائعة: تحديد ارتفاع ثابت مستقل عن العرض فيشوّه النسبة. ده شرح حساب لا تشغيل service كاملة من السطور الأربعة وحدها.

سؤال إنترفيو: التحويل لـWebP يثبت إن الملف آمن تمامًا؟

الإجابةلأ؛ لازم بقية pipeline والصلاحيات وحدود الذاكرة والملف والتعامل مع فشل الكتابة تكون محسوبة. الكود الحالي له مساحة تحسين، مش ضمان production شامل.

سؤال 4: أحصل على قائمة المنتجات بدون صور؟

مثال تدريبي إضافي على بيانات snapshot العامة؛ في Console صفحة Pizza المحلية:

const response = await fetch('/api/menu');
if (!response.ok) throw new Error('Menu failed');
const data = await response.json();
const missing = data.items.filter((item) => !item.image_path);
console.table(missing.map((item) => ({ id: item.id, name: item.name })));
  1. GET قائمة المنتجات.
  2. ارفض استجابة HTTP فاشلة بدل تحليلها كأنها menu.
  3. اقرأ JSON.
  4. filter ترجع المنتجات بدون path فقط؛ مش اختبار إن الملفات الموجودة قابلة للتحميل.
  5. map تختار id وname؛ ({ ... }) ترجع object من arrow function مختصرة؛ table تعرضها كجدول في Console.

بإيدك: قارن عدد النتائج ببيانات المصدر الحالية. متنسخش قائمة التقرير القديم كأنها نتيجة تشغيل النهارده.
